# Week 4 · Day 3 — MCP-инструмент с отложенным и периодическим выполнением

## Условие задания

Сделать MCP-инструмент с отложенным или периодическим выполнением: сохранять
данные в JSON или SQLite, выполнять работу по расписанию и возвращать
агрегированный результат.

**Результат:** MCP-сервер «метеожурнал» — фоновый планировщик по расписанию
опрашивает погоду наблюдаемых городов, копит замеры в SQLite, а инструменты
возвращают агрегированную статистику; приложение с агентом показывает полный
цикл «отложенное → периодическое → агрегат».

## Как устроено «расписание» внутри MCP

Ключевой архитектурный момент: **MCP — протокол запрос/ответ**. Сервер не может
сам «протолкнуть» данные клиенту — он только отвечает на вызовы. Поэтому
периодическая работа живёт **фоновой asyncio-задачей внутри сервера**:

```
агент (GLM) ◄──MCP (stdio)──► mcp_weather_journal_server.py
                                 │
                                 ├─ инструменты (по запросу клиента)
                                 │    watch_city · unwatch_city · list_watches
                                 │    collect_now · get_weather_stats
                                 │         │ читает
                                 │         ▼
                                 ├─ SQLite: watches ──── observations
                                 │         ▲ пишет
                                 └─ планировщик (asyncio-задача, каждые N сек):
                                      Open-Meteo → замер по каждому городу
```

Жизненным циклом управляет **lifespan** сервера: при старте — инициализировать
БД, создать HTTP-клиент и запустить `scheduler_loop`; при остановке — отменить
задачу и закрыть клиент. Всё это живёт в одном event loop с обработкой
инструментов, поэтому сбор и запросы не мешают друг другу.

**Отложенное выполнение** демонстрирует `watch_city`: вызов только регистрирует
город и честно отвечает «этот вызов погоду не измерял» — первый замер сделает
планировщик на ближайшем тике (`first_sample_in_sec`). Не хочется ждать —
`collect_now`.

Интервал планировщика задаётся переменной окружения `JOURNAL_INTERVAL_SEC`:
демо-приложение запускает сервер с **15 с** (иначе периодичность на
демонстрации ждать слишком долго), «боевой» дефолт сервера — **600 с**.

## Хранение и агрегаты — SQLite

Файл `weather_journal.db` (stdlib `sqlite3`, без зависимостей). Две таблицы:

```sql
watches       (id, city_key UNIQUE, name, country, latitude, longitude,
               timezone, created_at_utc, active)
observations  (id, watch_id → watches, observed_at_utc, local_time,
               temperature_c, feels_like_c, humidity_pct, precipitation_mm,
               wind_kph, weather_code, condition, source)
```

- `source` различает замеры планировщика (`scheduler`) и ручные (`collect_now`);
- `active=0` — город снят с наблюдения мягко: планировщик его больше не
  опрашивает, но история доступна `get_weather_stats`;
- данные **переживают перезапуск сервера**: города, поставленные в прошлой
  сессии, продолжают копиться в следующей (проверено живым прогоном ниже).

Агрегаты считает сам SQLite, а не Python — в этом и смысл выбора SQLite перед
JSON:

```sql
SELECT COUNT(*), AVG(temperature_c), MIN(temperature_c), MAX(temperature_c),
       AVG(feels_like_c), AVG(humidity_pct),
       SUM(precipitation_mm), MAX(wind_kph)
FROM observations WHERE watch_id = ? AND observed_at_utc >= ?   -- окно времени
```

Плюс доминирующая погода (`GROUP BY condition ORDER BY COUNT(*) DESC`) и
**тренд температуры** — средняя первой половины окна против второй
(`ROW_NUMBER() OVER ()`), с порогом ±0.5 °C: «потеплело / похолодало /
стабильно».

## Детали реализации

- **Фоновая задача и lifespan**: `scheduler_loop` стартует в `lifespan`
  (`MCPServer(..., lifespan=...)`), при остановке отменяется (`task.cancel()` +
  ожидание) — сервер не оставляет «висящих» задач; HTTP-клиент к Open-Meteo
  тоже живёт столько же, сколько сервер.
- **Первый тик — через интервал, не сразу**: это и есть «отложенное
  выполнение» — ответ `watch_city` (`first_sample_in_sec`) совпадает с тем,
  что реально делает планировщик.
- **SQLite из asyncio**: все запросы короткие и идут из одного потока event
  loop, поэтому синхронного `sqlite3` достаточно — блокировка незаметна,
  отдельные потоки/очереди не нужны.
- **Отказ одного города не валит сбор**: `collect_all` ловит исключения по
  каждому городу отдельно и пишет ошибку в отчёт/лог.
- **Ошибки — часть контракта** (как в day-2): пустое окно статистики — это
  `is_error=true` с подсказкой «ждите тик планировщика или вызовите
  collect_now», а не молчаливые нули.
- **Софт-удаление вместо каскада**: изначально `unwatch_city` удалял строку
  города, и `ON DELETE CASCADE` стирал его журнал — smoke-тест это поймал.
  Теперь `active=0`: планировщик город не трогает, история остаётся доступной
  `get_weather_stats` (проверено перезапуском сервера).
- **stderr вместо stdout**: логи `[планировщик]`/`[collect_now]` пишутся в
  stderr сервера (stdout занят JSON-RPC) и видны в консоли приложения —
  периодическая работа «ощутима» на демо.

## Выводы

- **«Расписание» в MCP — это фоновая задача внутри сервера, а не отдельный
  процесс-крон**: протокол не позволяет серверу инициировать передачу, поэтому
  планировщик молча копит данные, а клиент в любой момент читает накопленное
  инструментами. Паттерн «периодический сбор + агрегат по запросу» покрывает
  типовые задачи мониторинга.
- **SQLite окупается против JSON именно на агрегатах**: `AVG/MIN/MAX/SUM`,
  доминирующая погода через `GROUP BY` и тренд через оконные функции считает
  БД; плюс данные переживают перезапуск сервера, что и делает «периодичность»
  осмысленной.
- **Отложенный инструмент должен честно об этом говорить**: `watch_city`
  возвращает не только факт регистрации, но и `first_sample_in_sec` — модель
  (и пользователь) сразу понимает, когда ждать данные, вместо гадания.
- **Тестируй семантику, а не только «работает»**: smoke-тест без LLM (прямой
  вызов инструментов через MCP-клиент) поймал удаление истории при
  `unwatch_city` — дешевле, чем находить это в прогоне с агентом.
