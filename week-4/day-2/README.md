# Week 4 · Day 2 — Свой MCP-сервер вокруг API + вызов инструмента агентом

## Условие задания

Реализовать свой MCP-сервер вокруг API, описать параметры инструмента и
возвращаемый результат, подключить инструмент к агенту и показать вызов
из приложения.

**Результат:** работающий MCP-сервер поверх внешнего API + приложение с агентом,
который вызывает инструменты сервера через MCP и отвечает пользователю.

---

## Что сделано

| Файл | Роль |
|------|------|
| [`mcp_weather_server.py`](mcp_weather_server.py) | **MCP-сервер** (транспорт stdio) вокруг API [Open-Meteo](https://open-meteo.com) — бесплатного и без ключей |
| [`agent_app.py`](agent_app.py) | **Приложение**: MCP-клиент + агент на GLM (Z.ai) с tool-calling, печатающий трассировку вызовов |

Сервер экспонирует два инструмента, образующих цепочку:

| Инструмент | Оборачиваемое API | Вход | Выход |
|------------|-------------------|------|-------|
| `geocode_city` | Geocoding API | название города, язык | координаты, страна, часовой пояс, население |
| `get_weather_forecast` | Forecast API | широта, долгота, дни (1–7) | текущая погода + прогноз по дням |

Сервер не «проксирует» API в лоб: он скрывает сырой формат Open-Meteo
(плоские массивы `daily.time[]`, `daily.weather_code[]`, …), обогащает ответ
человекочитаемой расшифровкой кодов погоды WMO («пасмурно», «ливень»,
«гроза с градом») и возвращает нормализованную структуру.

---

## Как описаны параметры и результат

Контракт инструмента в MCP — это две JSON Schema, которые сервер публикует
сам в `tools/list` (клиент получает их при подключении, ничего хардкодить не надо).

**Вход — `inputSchema`** строится из аннотаций типов параметров:
`Annotated[float, Field(description=..., ge=-90, le=90)]` превращается в
описание + ограничения `minimum`/`maximum` прямо в схеме. Так параметр `days`
формально ограничен диапазоном 1–7 — неверный аргумент отклонится валидацией
до вызова функции:

```json
"days": {
  "default": 1,
  "description": "Число дней прогноза, 1–7",
  "maximum": 7, "minimum": 1,
  "type": "integer"
}
```

**Выход — `outputSchema`** строится из pydantic-модели возвращаемого типа
(`CityLocation`, `WeatherForecast` с вложенными `CurrentWeather`/`DailyForecast`):
каждое поле снабжено `Field(description=...)`, поэтому результат тоже формально
описан. При вызове сервер отдаёт и `structuredContent` (JSON по схеме), и
текстовое представление:

```json
"current": {
  "properties": {
    "temperature_c": {"description": "Температура воздуха на 2 м, °C", "type": "number"},
    "weather_code":  {"description": "Код погоды WMO (0 — ясно, 61 — дождь и т.д.)", "type": "integer"},
    "condition":     {"description": "Расшифровка кода погоды по-русски", "type": "string"}
  }
}
```

Ошибки — часть контракта: несуществующий город возвращает `is_error=true`
с внятным текстом («проверьте написание…»), который модель получает и может
исправить вызов.

## Как инструмент подключён к агенту

Приложение (`agent_app.py`) сводит MCP и tool-calling LLM:

```
user ──► LLM GLM (Z.ai, tools=[geocode_city, get_weather_forecast])
              │ tool_calls?
              ├── да ──► MCP session.call_tool() ──► structuredContent ──►
              │          сообщение role=tool ──► снова LLM (раунд 2, 3, …)
              └── нет ──► финальный ответ пользователю
```

1. **Подключение**: сервер запускается как подпроцесс (`stdio`), приложение делает
   `initialize` + `tools/list` — то же ядро клиента, что в day-1.
2. **Адаптация**: каждый MCP-инструмент конвертируется в формат OpenAI
   (`{"type": "function", "function": {name, description, parameters: inputSchema}}`).
3. **Цикл**: когда GLM отвечает `tool_calls`, приложение исполняет вызов через
   `session.call_tool()`, кладёт результат в сообщение `role=tool` и повторяет
   запрос — пока модель не даст финальный ответ (лимит 5 раундов как страховка).

Агентная логика — как в `AgentDemo` недель 2–3 (та же модель GLM через
coding-эндпоинт Z.ai), но инструменты теперь не зашиты в приложение,
а приходят по MCP от отдельного сервера.

## Живой прогон

Окружение: Python 3.14, MCP SDK `mcp` 2.3.0 (Windows), модель `glm-4.6`.

Вопрос по умолчанию — агент сам выстраивает цепочку из двух инструментов:

```
[MCP] initialize → соединение с open-meteo-weather v1.0.0
[MCP] tools/list → 2 инструмент(а): geocode_city, get_weather_forecast

[USER] Какая сейчас погода в Санкт-Петербурге и стоит ли брать зонт?

[РАУНД 1] LLM → MCP: call_tool geocode_city({"city": "Санкт-Петербург"})
[РАУНД 1] MCP → LLM: {"name": "Санкт-Петербург", "country": "Россия",
                      "latitude": 59.93863, "longitude": 30.31413,
                      "timezone": "Europe/Moscow", "population": 5351935}

[РАУНД 2] LLM → MCP: call_tool get_weather_forecast({"latitude": 59.93863, "longitude": 30.31413})
[РАУНД 2] MCP → LLM: {"location": "59.94°N, 30.31°E", "current": {"temperature_c": 8.2,
                      "feels_like_c": 3.0, "wind_kph": 27.0, "weather_code": 3,
                      "condition": "пасмурно"}, …}

[ASSISTANT] Сейчас в Санкт-Петербурге пасмурно:
            - 🌡 Температура: 8,2 °C (ощущается как 3 °C)
            - 💨 Ветер: 27 км/ч — ощутимо свежо
            - 💧 Осадки сейчас отсутствуют, вероятность дождя за день — около 22%

            **Зонт можно не брать**, но дождь не исключён полностью — если идёте
            надолго, компактный зонт не помешает. Главное — тёплая непродуваемая
            куртка: из-за ветра feels like всего +3 °C. 🧥
```

Второй вопрос — прогноз на неделю: агент **сам** выбрал `days: 7`
(уложился в ограничение схемы 1–7) и перепаковал `daily` в человеческий список:

```
[USER] Собираюсь на выходных в Ниццу. Какая там будет погода и что надеть?

[РАУНД 1] LLM → MCP: call_tool geocode_city({"city": "Ницца"})
[РАУНД 2] LLM → MCP: call_tool get_weather_forecast({"days": 7, "latitude": 43.70313, "longitude": 7.26608})

[ASSISTANT] Прогноз для Ниццы на ближайшую неделю:
            Пн 09.11: слабый дождь, +12…+17 °C, вероятность 80%
            Чт 12.11: сильный ливень (до ~48 мм!), вероятность 98%
            Пт 13.11 — Вс 15.11: пасмурно, без существенных осадков
            **Что надеть:** осенняя одежда; в первой половине недели обязательны
            зонт или непромокаемая куртка — особенно в четверг.
```

(Полные логи — без сокращений — воспроизводятся запуском `agent_app.py`.)

## Детали реализации

- **MCP SDK 2.x снова отличается от примеров**: `FastMCP` больше нет —
  сервер называется `MCPServer` (`from mcp.server.mcpserver import MCPServer`);
  поля объектов snake_case (`input_schema`, `structured_content`, `is_error`).
- **Структурированный вывод включается аннотацией возвращаемого типа**:
  pydantic-модель в сигнатуре инструмента → сервер сам строит `outputSchema`,
  валидирует результат и отдаёт `structuredContent`.
- **stdio-сервер молчит в stdout** (он занят JSON-RPC); httpx-логи приглушены
  до WARNING, чтобы не шуметь в консоли родителя.
- **Ключ нужен только агенту** (LLM): сам погодный сервер работает без ключей —
  демо-инфраструктура не зависит от подписок, кроме GLM Coding Plan.
- Аргументы `tool_calls` от LLM приходят JSON-строкой — разворачиваются
  `json.loads` перед `call_tool`; ошибки инструмента не роняют цикл, а
  возвращаются модели текстом для самокоррекции.

## Выводы

- **Схемы — это «API договора» для модели**: описания параметров и ограничений
  в `inputSchema` GLM читает и использует — в прогоне агент самостоятельно
  передал координаты из первого инструмента во второй и выбрал корректный `days`.
- **`outputSchema` + `structuredContent` делают результат инструмента
  машиночитаемым**: агент получает типизированный JSON, а не парсит текст.
- **MCP-сервер — способ вынести интеграцию из приложения**: погодная логика
  (два HTTP API, WMO-коды, нормализация) живёт в отдельном процессе, а приложение
  лишь дёргает `call_tool` — сервер можно переиспользовать из любого
  MCP-клиента, не только из этого агента.
