# Week 4 · Day 5 — MCP Orchestration: мульти-серверный пайплайн

## Условие задания

Зарегистрировать несколько MCP-серверов. Агент должен выбрать инструменты,
маршрутизировать вызовы и выполнить длинный сценарий с инструментами
разных серверов.

**Результат:** приложение-оркестратор, поднимающее **четыре** MCP-сервера
одновременно (три переиспользованы из дней 2–4 без единой правки + один
новый), с реестром инструментов «сервер__инструмент» и агентом GLM, который
сам выбирает инструменты, а приложение доставляет каждый вызов в сессию
нужного сервера. Длинный демо-сценарий «спланируй поездку» делает 17
вызовов через все четыре сервера.

---

## Что сделано

| Файл | Роль |
|------|------|
| [`agent_app.py`](agent_app.py) | **Приложение-оркестратор**: 4 MCP-подпроцесса → реестр маршрутизации → агент GLM (Z.ai) с tool-calling + 2 демо-сценария + счётчик маршрутизации + smoke-режим |
| [`mcp_travel_kit_server.py`](mcp_travel_kit_server.py) | **Новый MCP-сервер** «travel-kit» (stdio, без сети): одежда, чек-лист, оценка погоды для поездки — детерминированные правила |
| [`mcp_weather_server.py`](mcp_weather_server.py) | Копия из day-2 (без изменений): геокодинг + прогноз Open-Meteo |
| [`mcp_weather_journal_server.py`](mcp_weather_journal_server.py) | Копия из day-3 (без изменений): наблюдение за городами, SQLite + планировщик |
| [`mcp_pipeline_server.py`](mcp_pipeline_server.py) | Копия из day-4 (без изменений): конвейер «получение → обработка → сохранение» + аудит |

Четыре сервера — 16 инструментов в одном реестре:

| Сервер (префикс) | Происхождение | Инструменты |
|------------------|---------------|-------------|
| `weather__` | day-2 | `geocode_city`, `get_weather_forecast` |
| `journal__` | day-3 | `watch_city`, `unwatch_city`, `list_watches`, `collect_now`, `get_weather_stats` |
| `pipeline__` | day-4 | `fetch_weather`, `analyze_data`, `save_report`, `run_pipeline`, `inspect_run`, `list_reports` |
| `travel__` | **day-5 (новый)** | `recommend_clothing`, `build_checklist`, `score_travel_weather` |

Новый сервер `travel-kit` выбран без сети намеренно: три погодных сервера
недели ходят во внешний мир (Open-Meteo, LLM, SQLite), а travel-kit — чистые
правила. Он замыкает длинный сценарий: агрегаты, полученные с других
серверов, агент подаёт на вход его инструментам и получает финальный совет.

## Как устроены регистрация и маршрутизация

```
                 ┌──────────────────────────────────────────────────┐
                 │  agent_app.py (оркестратор)                      │
                 │                                                  │
                 │  РЕЕСТР: "weather__geocode_city" → Route(        │
                 │            alias="weather", session №1,          │
                 │            tool_name="geocode_city")             │
                 │  … 16 записей, по одной на инструмент            │
                 └───────▲──────────────────────────────────────────┘
                         │ tool_call: "journal__collect_now"  ← выбор за LLM
 user ──► GLM (16 tools с префиксами серверов)
                         │ доставка по реестру — за приложением
      ┌──────────────────┼─────────────────────┬───────────────────┐
      ▼                  ▼                     ▼                   ▼
 stdio-сессия 1     stdio-сессия 2        stdio-сессия 3      stdio-сессия 4
 weather (day-2)    journal (day-3)       pipeline (day-4)    travel (day-5)
```

1. **Регистрация**: `AsyncExitStack` открывает 4 транспорта `stdio_client`
   и 4 `ClientSession` (без восьмикратной вложенности `async with`), для
   каждой сессии — `initialize` + `tools/list`.
2. **Реестр**: каждому инструменту даётся полное имя
   `сервер__инструмент` — так его видит LLM. Префикс решает сразу две
   задачи: маршрутизация (имя содержит адрес) и отсутствие конфликтов
   (два сервера могут иметь одинаковые имена инструментов).
3. **Выбор** — за моделью: все 16 инструментов уходят в LLM в формате
   OpenAI tools с префиксом в имени и пометкой сервера в описании.
4. **Доставка** — за приложением: по имени из `tool_calls` берётся
   `Route` с сессией нужного сервера, вызов идёт в неё, результат —
   обратно в LLM. Трассировка показывает маршрут: `LLM → MCP[journal]`.
5. **Незарегистрированное имя** не роняет цикл: модель получает ошибку
   маршрутизации со списком доступных префиксов и исправляет вызов.

**Данные между серверами передаёт агент, а не серверы**: координаты из
`weather__geocode_city` — в `weather__get_weather_forecast`; агрегаты из
`pipeline__run_pipeline` (средняя температура, дождливые дни, ветер) — в
`travel__score_travel_weather` / `travel__build_checklist`. Серверы друг
о друге не знают — связность живёт на уровне оркестратора, и она видна
в трассировке раундов.

## Как запустить

```bash
cd week-4/day-5
python -m venv venv
venv\Scripts\python.exe -m pip install -r requirements.txt   # Windows
# скопировать .env.example → .env и вписать ZAI_API_KEY (агенту И pipeline-
# серверу для LLM-анализа; без ключа конвейер уйдёт на правила)
venv\Scripts\python.exe agent_app.py --smoke   # проверка 4 серверов без LLM
venv\Scripts\python.exe agent_app.py           # демо: длинный сценарий + свободный выбор
venv\Scripts\python.exe agent_app.py "вопрос"  # свой вопрос агенту
```

Демо-сценарии: **ДЕМО 1** — «спланируй поездку в Сочи» с явным планом по
всем четырём серверам; **ДЕМО 2** — сравнение городов без подсказок, каким
сервером пользоваться (модель сама выбирает инструменты и маршрут).
`pipeline.db`, `weather_journal.db` и `reports/` создаются автоматически.

Окружение: Python 3.14.2, MCP SDK `mcp` 2.3.0 (Windows), модель `glm-4.6`.
Перед прогоном с агентом — smoke-тест (`--smoke`): по одному прямому вызову

## Детали реализации

- **N серверов без пирамиды `async with`**: `AsyncExitStack` держит все
  4 транспорта и 4 сессии открытыми до конца `main` — добавить пятый
  сервер = одна строка в `SERVERS`.
- **Префикс `сервер__инструмент`**: имя проходит валидацию tools у LLM
  (буквы/цифры/подчёркивания), несёт маршрут и снимает коллизии имён
  между серверами; при регистрации дубликаты ловятся явно.
- **`sys.exit` нельзя бросать внутри `async with AsyncExitStack`**:
  `SystemExit` на размотке anyio-таскграупдов оборачивается в
  `ExceptionGroup` и процесс завершается кодом 1. `main()` возвращает код
  выхода, `sys.exit(asyncio.run(main()))` — уже снаружи (поймано smoke-
  тестом: вызовы все зелёные, а exit-код 1 и простыня трейсбека).
- **Пачки tool_calls — фича GLM**: модель группирует независимые вызовы в
  один раунд (в DEMO 1 — пять сразу) и ставит зависимые после получения
  результатов (в DEMO 2 — сначала два геокодинга, затем два прогноза с
  точными координатами). Побочный эффект заметен в DEMO 1: прогноз в том
  же раунде, что и геокодинг, модель запросила по «своим» координатам
  Сочи (43.5855/39.7231 против 43.59699/39.72477 из геокодинга) — точки
  в километре друг от друга, на погоду не влияет, но артефакт батчинга
  виден и о нём стоит знать.
- **Планировщик journal приглушён**: `JOURNAL_INTERVAL_SEC=3600` (в day-3
  он тикал каждые 15 с ради демонстрации периодичности) — в мульти-
  серверном демо замер делает `collect_now`, ждать тики незачем.
- **Серверы дней 2–4 не правились вовсе**: скопированы как есть. Это и
  есть главная проверка переносимости MCP: сервер, написанный для своего
  дня, встал в чужой пайплайн без изменений.
- **Счётчик маршрутизации** (`Counter` по алиасу сервера) печатается в
  конце — дешёвое доказательство, что сценарий действительно
  мульти-серверный, а не «один сервер и мелочь».

## Выводы

- **Регистрация нескольких серверов — это реестр «имя → сессия»**. Префикс
  сервера в имени инструмента делает маршрутизацию тривиальной и для
  клиента, и для модели: LLM выбирает инструмент по полному имени, клиент
  просто смотрит, в какую сессию его отправить.
- **Настоящая сложность мульти-серверности — не маршрутизация, а передача
  данных**: серверы друг о друге не знают, и связность (координаты →
  прогноз → агрегаты → советы) живёт в агенте. В трассировке раундов
  видно, как идентификаторы и агрегаты перетекают между префиксами.
- **Ошибки валидации — часть контракта**: отказ `build_checklist` с
  внятным текстом вернул модель к правильному вызову за один раунд, без
  падения сценария.
- **MCP-серверы переносимы по-настоящему**: три сервера трёх предыдущих
  дней заработали в новой конфигурации без единой правки — неделю
  стоило строить именно так, чтобы день 5 стал проверкой архитектуры.
