# Week 4 · Day 4 — MCP Composition: автоматический конвейер (Auto Pipeline)

## Условие задания

Создать несколько MCP-инструментов и автоматическую цепочку:
**получение данных → обработка → сохранение**. Проверить выполнение цепочки
и передачу данных.

**Результат:** MCP-сервер «weather-pipeline» с конвейером из трёх стадий, где
данные передаются между стадиями по `artifact_id`, а факт передачи проверяется
sha256-хэшем; агент GLM демонстрирует два режима композиции — серверный
(`run_pipeline`) и агентский (сам передаёт идентификаторы между инструментами).

---

## Что сделано

| Файл | Роль |
|------|------|
| [`mcp_pipeline_server.py`](mcp_pipeline_server.py) | **MCP-сервер** (stdio): артефакты стадий в SQLite, автоцепочка `run_pipeline`, аудит `inspect_run`, LLM-анализ через GLM (Z.ai) с fallback на правила |
| [`agent_app.py`](agent_app.py) | **Приложение**: MCP-клиент + агент GLM (Z.ai) с tool-calling (мост переиспользован из day-2/3) + два демо композиции |

Шесть инструментов — три стадии конвейера, оркестратор, аудитор и справка:

| Инструмент | Стадия / роль | Что делает | Возвращает |
|------------|---------------|------------|------------|
| `fetch_weather` | 1 · получение данных | Open-Meteo: геокодинг + погода сейчас + прогноз 7 дней → артефакт `raw_weather` | `artifact_id`, `payload_hash` |
| `analyze_data` | 2 · обработка | агрегаты (средняя/мин/макс, осадки, дождливые дни, доминирующая погода) + текстовый вывод **LLM GLM** (fallback — правила) → артефакт `weather_analysis` | `artifact_id`, `source_artifact_id`, агрегаты |
| `save_report` | 3 · сохранение | отчёт в SQLite + JSON-файл `reports/report_NNN.json` с блоком lineage | `report_id`, `file_path`, `lineage.matches` |
| `run_pipeline` | **автоцепочка** | сервер сам гоняет fetch → analyze → save, журналируя каждую стадию | `run_id`, постадийный лог, отчёт |
| `inspect_run` | **аудит** | проверка выполнения цепочки и передачи данных (6 проверок) | `checks[]`, `all_ok`, вердикт |
| `list_reports` | справка | последние сохранённые отчёты | список |

Развитие дней 2–3: там агент вызывал инструменты по одному, здесь —
**композиция**: данные стадии передаются по ссылке (`artifact:N`), а их
целостность доказуема хэшем.

---

## Как устроена композиция

```
агент (GLM) ◄──MCP (stdio)──► mcp_pipeline_server.py
     │                            │
     │ run_pipeline(city)         ├── СТАДИЯ 1 fetch:  Open-Meteo ──► artifact:1 (raw_weather, sha256)
     │ или три вызова вручную     ├── СТАДИЯ 2 analyze: агрегаты + LLM ──► artifact:2 (weather_analysis,
     │                            │                                source_artifact_id=1, input_hash)
     └── inspect_run(run_id)      ├── СТАДИЯ 3 save:   SQLite + report_001.json (lineage)
                                  └── журнал: runs ──── stages (вход/выход, статус, мс)
```

**Два режима композиции:**

- **серверный** — `run_pipeline(city)`: оркестратор — сам сервер. Каждая стадия
  логируется в таблицу `stages` (`input_ref`/`output_ref`, статус, длительность);
  при падении любой стадии запуск помечается `failed`, а `inspect_run` честно
  покажет, где порвалась цепочка;
- **агентский** — LLM сама выступает оркестратором: вызывает `fetch_weather` →
  `analyze_data(artifact_id от fetch)` → `save_report(artifact_id от analyze)`,
  передавая идентификаторы между раундами (передача данных видна в трассировке).

**Передача данных доказуема, а не «на доверии»:**

- каждый артефакт хранит канонический JSON + **sha256** (`payload_hash`);
- артефакт анализа фиксирует `source_artifact_id` и `input_payload_hash` —
  хэш данных *в момент обработки*;
- `inspect_run` **пересчитывает** хэш исходного артефакта и сверяет с
  зафиксированным: совпал — данные дошли fetch → analyze без изменений;
- `save_report` делает ту же сверку на месте (`lineage.matches`) и кладёт
  родословную в JSON-отчёт — проверка есть и у ручной цепочки, не только у
  автоцепочки.

---

## Аудит цепочки — `inspect_run(run_id)`

Шесть проверок, каждая с человеческим пояснением:

| Проверка | Что проверяет |
|----------|---------------|
| `run_status` | запуск завершился со статусом `ok` |
| `stage_sequence` | стадии ровно три, в порядке fetch → analyze → save, все `ok` |
| `chain_links` | связность ссылок: выход стадии N == входу стадии N+1 (`artifact:N`) |
| `artifact_kinds` | виды артефактов: `raw_weather` → `weather_analysis` |
| `data_integrity` | **sha256 исходных данных == хэшу при обработке** — данные дошли без изменений |
| `report_saved` | отчёт есть в SQLite, ссылается на артефакт анализа, файл на диске непуст |

`all_ok=true` — цепочка выполнена полностью и данные прошли все стадии;
иначе вердикт перечисляет проваленные проверки по именам.

## Детали реализации

- **Схема SQLite**: `artifacts` (kind, канонический JSON, sha256), `runs` +
  `stages` (журнал автоцепочки: вход/выход-ссылки, статус, мс), `reports`
  (сохранённые отчёты). Канонический JSON (`sort_keys`, без пробелов) —
  гарантия, что одинаковые данные дают одинаковый хэш на любых стадиях.
- **Ядра стадий вынесены в `do_*`**: их вызывают и отдельные инструменты, и
  `run_pipeline` — ручная и автоматическая цепочки делают ровно одно и то же,
  разница только в том, кто передаёт `artifact_id` (LLM или сервер).
- **LLM на стадии обработки**: тот же coding-эндпоинт Z.ai, что у агента
  (`thinking: disabled`, `max_tokens: 400`); нет ключа или сбой — вывод
  собирается по правилам, `summary_source: "llm" | "rules"` честно сообщает,
  каким путём. Конвейер не ломается из-за внешней зависимости.
- **Отказ стадии не теряется**: `run_pipeline` при исключении пишет стадию со
  статусом `failed`, завершает run с ошибкой и поднимает `ToolError` с
  подсказкой `inspect_run(run_id=…)` — аудиту всё равно есть что проверить.
- **Smoke-тест снова окупился**: он поймал `NameError` в `do_save`
  (walrus-выражение затирало переменную с исходными данными) ещё до прогона
  с агентом — секунды вместо минут отладки в живом демо.
- **`.gitignore` дня** прячет `pipeline.db`, `reports/`, `venv/` и `.env`:
  в репозитории — только код и документация.

## Выводы

- **Композиция MCP-инструментов живёт на двух уровнях**: сервер может
  собрать цепочку сам (`run_pipeline`), а может оставить оркестрацию агенту —
  тогда LLM передаёт идентификаторы между вызовами, и это видно в трассировке
  раундов. Оба режима полезны: первый — детерминированность, второй — гибкость.
- **Передачу данных надо делать проверяемой**: ссылка `artifact:N` + sha256
  превращают «мне кажется, данные дошли» в формальный аудит из шести проверок.
  Хэш, зафиксированный при обработке и пересчитанный при аудите, — это
  доказательство неизменности данных в цепочке.
- **Журнал стадий — дешёвая наблюдаемость**: таблица `stages` со ссылками
  вход/выход и длительностями отвечает на вопросы «где порвалось» и «что
  тормозит» без дополнительных логов.
- **AI-стадия в конвейере должна деградировать, а не падать**: LLM-вывод на
  стадии обработки закрыт fallback-правилами с честной пометкой источника —
  внешняя зависимость не роняет цепочку.
