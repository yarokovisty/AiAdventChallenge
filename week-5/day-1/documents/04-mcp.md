# Model Context Protocol

MCP (Model Context Protocol) — открытый протокол подключения инструментов и данных к моделям. До MCP каждый интегратор придумывал свой формат «модель ↔ инструменты»; MCP стандартизовал этот стык, и теперь один MCP-сервер работает с любым совместимым клиентом.

## Зачем нужен MCP

Проблема, которую решает протокол, — комбинаторика интеграций. Было: M моделей и N инструментов требуют M×N bespoke-обвязок. Стало: каждый инструмент оборачивается в MCP-сервер один раз, каждая модель подключается к протоколу один раз, и любые инструменты доступны любым клиентам. Дополнительный выигрыш — переиспользование: сервер, написанный для одного агента, без правок работает во всех остальных: хоть в IDE, хоть в чат-боте, хоть в пайплайне.

## Архитектура: клиент, сервер, транспорт

В архитектуре три роли: MCP-клиент (живёт внутри приложения-хоста, например агента), MCP-сервер (поставщик возможностей) и транспорт (как именно ходят сообщения). Возможности сервера описываются в трёх категориях: инструменты — функции, которые модель может вызывать; ресурсы — данные, которые можно читать; промпты — готовые шаблоны. При соединении клиент и сервер делают handshake: обмениваются версииями протокола и списком возможностей.

### Транспорт stdio

Stdio-транспорт запускает сервер как локальный подпроцесс: клиент пишет JSON-сообщения в stdin сервера и читает ответы из stdout. Это самый простой путь: не нужны ни сеть, ни ключи, ни инфраструктура — сервер поднимается вместе с клиентом и умирает вместе с ним. Ограничение очевидно: stdio работает только на одной машине, удалённо такой сервер не поднять.

### Транспорт Streamable HTTP

Streamable HTTP — транспорт для удалённых серверов: клиент и сервер общаются HTTP-запросами, сообщения могут стримиться потоком (SSE), состояние сессии держится в заголовке Mcp-Session-Id. Такой сервер живёт где угодно — за балансировщиком, в облаке, у стороннего провайдера — и авторизуется обычными HTTP-механизмами вроде Bearer-токена. Плата за это — необходимость управлять сетью, аутентификацией и временем жизни сессий.

## Инструменты, ресурсы и промпты

- **tools** — вызываемые функции: `tools/list` возвращает список с JSON-схемами аргументов, `tools/call` исполняет вызов;
- **resources** — читаемые данные по URI: файлы, записи справочников, результаты наблюдений;
- **prompts** — библиотека готовых промптов-шаблонов с параметрами.

## Мульти-серверная оркестрация

Реальные агенты подключают несколько серверов сразу: погода из одного, календарь из другого, база знаний из третьего. Задачи оркестрации: маршрутизация вызова нужному серверу (обычно через префикс имени `сервер__инструмент`), разрешение конфликтов имён и передача данных между серверами. Последнее — самое интересное: серверы друг о друге не знают, и связывающим звеном выступает сама модель — результат одного вызова она подставляет в аргументы другого. Один длинный сценарий легко задействует три-четыре сервера по кругу, поэтому оркестратор обязан вести учёт: какой вызов в какой сервер ушёл, что вернулось и сколько это стоило.

## Пайплайны из инструментов

Следующий шаг после оркестрации — автоматизация: последовательность вызовов инструментов собирается в пайплайн, где выход одного шага становится входом следующего. Пайплайн можно собирать вручную или поручить модели. Ценность — воспроизводимость: сохранённый пайплайн прогоняется повторно с новыми данными без ручных кликов, а журнал шагов даёт прозрачность: каждое промежуточное состояние можно посмотреть и проверить.
