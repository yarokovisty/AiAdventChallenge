# Week 5 · Day 2 — First RAG Query + Comparison

## Условие задания

Реализовать цепочку **«вопрос → поиск релевантных чанков → контекст и вопрос →
LLM»**, сравнить ответы **с RAG и без него**. Подготовить **10 контрольных
вопросов** с ожидаемыми фактами и источниками.

**Результат:** скрипт [`rag_query.py`](rag_query.py) — первый полноценный
RAG-запрос по индексу из [day-1](../day-1/) — и файл
[`eval_questions.json`](eval_questions.json) с 10 контрольными вопросами.
Прогон на Z.ai GLM: с RAG **16/16 фактов, 10/10 источников**, без RAG —
**8/16 фактов, 0/10 источников**.

---

## Что сделано

| Файл | Роль |
|------|------|
| [`rag_query.py`](rag_query.py) | RAG-цепочка: вопрос → эмбеддинг → топ-K чанков → промпт «контекст + вопрос» → glm-4.6; режим «без RAG»; авто-оценка по контрольным вопросам |
| [`eval_questions.json`](eval_questions.json) | 10 контрольных вопросов: ожидаемые факты (с вариантами написания для авточека) + эталонный источник (документ › секция) |
| `results/eval_*.json` | Артефакты прогона: ответы обоих режимов, найденные чанки, метрики (генерируются, gitignored) |

Индекс и корпус не дублируются — используется индекс **structured** из day-1
(`../day-1/index/structured.json`, 42 чанка, победитель сравнения стратегий).
Эмбеддер запросов — та же модель `intfloat/multilingual-e5-small`, что строила
индекс (имя читается из метаданных индекса: запрос и чанки обязаны
кодироваться одной моделью, с префиксом `query:`).

```
                        ┌──────────────────────────────────────────────┐
  «вопрос» ─► e5 query: │  косинусная близость с 42 чанками индекса    │
              эмбеддинг │  structured (day-1)                          │
                        └──────────────┬───────────────────────────────┘
                                       ▼
                                топ-K = 4 чанка (doc, секция, скор)
                                       │
              ┌────────────────────────┴───────────────────────┐
              ▼ БЕЗ RAG                                        ▼ С RAG
  system + вопрос                          system («только по контексту,
  (контекста нет)                           цитируй источник»)
              │                             + контекст [1..4] + вопрос
              └──────────────┬───────────────────────────────┘
                             ▼
                 glm-4.6 @ Z.ai, temperature = 0, thinking off
                             │
                             ▼
                авточек: факты + цитирование + качество поиска
```

Сравнение честное: режимы отличаются **только наличием контекста** — одна
модель (`glm-4.6`), один `temperature=0`, одинаковая лаконичность system-промпта.
Сетевые сбои LLM-вызова ретраятся один раз (в живом прогоне как раз случился
`ConnectionResetError` на Q07 — прогон продолжился).

## Контрольные вопросы

10 вопросов, по 2 на каждый из 5 документов. Принцип отбора: **корпус-специфичные
проверяемые факты** — точные значения, формулировки и термины из заметок курса,
которые нельзя «угадать» из общих знаний (плюс пара общих вопросов для
контраста). Полные формулировки и варианты — в `eval_questions.json`.

| # | Вопрос (суть) | Ожидаемые факты | Источник |
|---|---------------|-----------------|----------|
| Q01 | Стартовое значение temperature и диапазон для творческих задач | **0.7**; **0.8–1.2** | 01-prompting › Temperature |
| Q02 | Few-shot пример противоречит system-промпту — что победит? | **пример** | 01-prompting › Few-shot |
| Q03 | Чем плох молчаливый `null` на месте результата инструмента? | модель **додумает** причину и **продолжит** | 02-agents › Обработка ошибок |
| Q04 | Зачем агентному циклу лимит шагов? | страховка от **зацикливания**; **бюджет** на токены | 02-agents › Agent loop |
| Q05 | Три стратегии сжатия диалога | **окно**; **резюме**; **вынесенные факты** | 03-context › Сжатие |
| Q06 | Почему «символы ÷ 4» занижает расход токенов для русского? | слово дробится на **2–3 токена** | 03-context › Окно и токены |
| Q07 | Сколько bespoke-обвязок до MCP для M моделей и N инструментов? | **M×N** | 04-mcp › Зачем нужен MCP |
| Q08 | В каком HTTP-заголовке Streamable HTTP хранит id сессии? | **Mcp-Session-Id** | 04-mcp › Streamable HTTP |
| Q09 | Какой overlap рекомендуют при фиксированном чанкинге? | **10–20%** | 05-rag › Фиксированный размер |
| Q10 | Метрики поискового звена RAG | **hit@k**; **MRR** | 05-rag › Оценка качества |

Авто-оценка трёх слоёв, отдельно друг от друга:

1. **Поиск** (до LLM): hit@1 / hit@K по документу, попадание top-1 в эталонную
   секцию — так видно, что виновато: чанкинг с эмбеддингами или генерация;
2. **Факты**: каждый факт задан списком допустимых формулировок (`0.8–1.2`,
   `0,8-1,2`, «от 0.8 до 1.2»…), проверка — вхождение в ответ;
3. **Цитирование**: назван ли ожидаемый документ (`01-prompting-basics.md`).

## Результат сравнения

Окружение: glm-4.6 (Z.ai coding endpoint), temperature=0, top-K=4,
индекс structured из day-1. Прогон: `results/eval_20261122_162723.json`.

| Метрика | без RAG | с RAG |
|---|---|---|
| **Фактов подтверждено** (из 16) | 8 | **16** |
| **Вопросов со всеми фактами** (из 10) | 4 | **10** |
| **Источник-документ назван** (из 10) | 0 | **10** |
| Поиск: hit@1 / hit@K / эталонная секция | — | 10/10 · 10/10 · 10/10 |

### Показательные расхождения

**Q02 — прямое противоречие базы и общих знаний.** Без RAG glm-4.6 уверенно
заявил: «system-промпт обычно имеет больший вес». В базе знаний курса правило
другое: «если пример противоречит system-промпту, **победит пример**». С RAG
модель ответила по базе и процитировала источник. Это главный аргумент RAG:
не «модель глупая», а «у модели своё мнение из обучающих данных, а нужна
правда этой конкретной базы».

**Q01 — правдоподобные, но чужие числа.** Без RAG: «начинать с 1.0, для
творческих 0.7–1.2, иногда до 1.5–2.0». Звучит грамотно, но не совпадает с
базой: старт — **0.7**, творческий диапазон — **0.8–1.2**. С RAG — точные
значения из заметок.

**Q05 — своя классификация вместо нашей.** Без RAG модель перечислила
truncation/summarization (1/3 фактов) — общеупотребимый, но не наш список.
С RAG — ровно три стратегии базы: окно, резюме, вынесенные факты.

**Q07, Q08 — общие знания, где RAG не добавил фактов.** И `M×N`, и
`Mcp-Session-Id` glm-4.6 знает сам: оба режима правы. Но только RAG-ответ
сослался на документ и раздел — проверяемость появляется даже там, где
RAG «не нужен» для точности.

## Выводы

- **RAG решает задачу дня точно:** все 16 фактов из 16, все 10 источников, и
  все 10 эталонных секций найдены поиском. Без RAG — 8/16 фактов и ни одной
  ссылки на источник.
- **Главная ценность RAG — не «умнее», а «из нужной базы»:** конфликт Q02
  (system-промпт vs пример) модель без контекста решает по общим представлениям
  — и проигрывает. Правдоподобие ≠ истинность: численные ответы без RAG
  (Q01, Q05) выглядели компетентно, но не совпадали с базой.
- **Проверяемость — бесплатный побочный эффект:** даже на вопросах, которые
  модель знает сама (Q07 `M×N`, Q08 `Mcp-Session-Id`), RAG-режим даёт источник
  `[документ › раздел]`, который можно показать пользователю. Без RAG — 0/10
  цитирований.
- **Раздельная оценка фаз окупается:** поиск (hit@1, секция) и генерация
  (факты, цитирование) меряются независимо — сразу видно, что слабое звено
  здесь не поиск, а «память» модели без контекста.
- **Две честные оговорки.** Во-первых, temperature=0 не гарантирует
  идентичности ответов между прогонами (два прогона дали без RAG 9/16 и 8/16
  фактов — плавает «правдоподобная» часть, тогда как RAG-ответы, привязанные
  к контексту, стабильны). Во-вторых, авточек по подстрокам — эвристика: он
  не понимает семантику и допускает граничные случаи (например, «0.7» внутри
  чужого диапазона «0.7–1.2» засчитано как факт Q01) — цена автоматизации,
  для точного вердикта нужны LLM-асессоры.
