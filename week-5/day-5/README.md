# Week 5 · Day 5 — RAG-чат с историей и памятью задачи

## Условие задания

Мини-чат хранит историю диалога, при каждом новом вопросе ищет контекст через
RAG, отвечает по найденной информации и выводит источники. Усиление — **память
задачи**: цель, уточнения, ограничения и термины. Проверка — два длинных
сценария по 10–15 сообщений.

**Результат:** скрипт [`rag_chat.py`](rag_chat.py) — чат, где каждый ход
проходит через `память задачи → query rewrite с историей → векторный поиск →
реранк с порогом → генерация с историей и памятью (строгий JSON: ответ +
источники + цитаты) → пост-валидация → faithfulness-судья`. Два сценария по 13
сообщений в [`scenarios.json`](scenarios.json) проверяют: разрешение follow-up'
ов с местоимениями, влияние памяти на поиск и ответы, честный отказ на
вне-корпусных вопросах, ответы на вопросы о самом диалоге из истории.

### Схема хода

```
сообщение пользователя
      │
      ├─ [0] ПАМЯТЬ ЗАДАЧИ (1 LLM-вызов, ДО ответа — чтобы повлиять на него):
      │       извлечение цели/уточнений/ограничений/терминов → детерминированный
      │       merge; заодно классификация сообщения:
      │       • meta_only (правила или цель без вопроса к базе) → короткое
      │         подтверждение «Принято…», RAG не вызывается вовсе;
      │       • needs_history (вопрос о самом диалоге: «напомни, о чём мы
      │         говорили») → ответ из истории и памяти, без поиска по базе;
      │       • иначе — обычный RAG-ход:
      │
      ├─ [1] query rewrite С ИСТОРИЕЙ И ПАМЯТЬЮ: follow-up с местоимениями
      │       («а если я перееду с ним на VPS?») → самодостаточный поисковый
      │       запрос («MCP-сервер на VPS — транспорт Streamable HTTP…»)
      ├─ [2] векторный поиск (e5) → топ-K1 = 8 кандидатов
      ├─ [3] LLM-реранкер 0–10 + ПОРОГ (2) → топ-K2 = 3 чанка
      │       └─ пусто → «не знаю» + просьба уточнить (генерация не зовётся)
      ├─ [4] генерация (строгий JSON): чанки с chunk_id-паспортами + окно
      │       истории + ПАМЯТЬ (ограничения обязательны к исполнению)
      │       → {answer, sources, quotes}
      ├─ [5] пост-валидация источников/цитат + faithfulness-судья (из day-4)
      └─ [6] термины: ответ на «что такое X» (усечённый) детерминированно
              попадает в глоссарий памяти — термин переживает окно истории
```

### Память задачи

Явная структура `TaskMemory` с четырья полями — ровно по заданию:

| Поле | Что хранит | Как попадает | Как влияет |
|---|---|---|---|
| **goal** | цель пользователя одной фразой | LLM-извлечение из сообщения, где цель явно сформулирована | rewrite понимает «мой выбор», генерация держит фокус |
| **clarifications** | факты об условиях задачи (окружение, ресурсы) | LLM-извлечение | rewrite разворачивает «моей ситуации» в конкретные термины |
| **constraints** | правила, обязательные в ответах (формат, запреты) | LLM-извлечение | инжектятся в промпт генерации; проверяются авточеками (например, «без кода») |
| **terms** | глоссарий: термин → определение из ответа | детерминированно: ответ на «что такое X» → первые 240 символов | термин живёт в памяти, даже когда ход выпал из окна истории |

Принципы: **merge детерминированный** — LLM возвращает только добавления
(`add_constraints`, …) и цель, а код применяет их с дедупликацией по
нормализованному ключу; LLM никогда не переписывает память напрямую.
Извлечение выполняется **до** ответа — ограничение из текущего сообщения
(«отвечай коротко и без кода») действует уже на текущий ответ.

### История диалога

История хранится полностью, в промпты идёт **окном**: rewrite видит последние
4 хода (его работа — разрешить местоимения), генерация — последние 6 ходов
(связность ответа с предыдущими). Для вопросов «о самом диалоге»
(`needs_history`) в промпт уходит вся история целиком. Сжатие истории (окно /
резюме / факты) — тема [week-2](../../week-2/), здесь базовое окно достаточно:
сценарии по 13 сообщений.

### Показательные места

**Follow-up с местоимением (S2-M04).** «А если месяца через три я перееду **с
ним** на VPS — что мне тогда понадобится?» — «с ним» разрешается через
историю+память в самодостаточный запрос «Что потребуется для перевода
MCP-сервера с stdio-транспортом на удалённый VPS…», поиск находит чанк
Streamable HTTP (скор 9), ответ с двумя источниками и дословными цитатами,
`supported`. Без истории такой запрос искал бы «переезд с ним» — мусор.

**Память вместо переспрашивания (S2-M10).** «Что лучше всего подходит для
**моей ситуации**?» — rewrite разворачивает «мою ситуацию» (сервер на одной
машине, нулевой бюджет из памяти) в «…для MCP-сервера, работающего [локально]»,
ответ: «Сейчас (сервер на одной машине с клиентом) оптимален stdio: самый
простой вариант без сети, ключей и инфраструктуры. Через ~3 месяца при
переезде на…» — условие из сообщения №2 и план из №4 работают через 8 ходов.

**Ограничение живёт после ввода (S1-M06 → все ответы дальше).** После «отвечай
коротко, простыми словами и совсем без кода» все 6 последующих RAG-ответов —
без кода (детерминированный чек ` ``` ` → 12/12 по обоим сценариям), ответ на
финальный «собери всё» даже получил приписку rewrite «…кратко простыми словами
без кода» — ограничение доехало до поискового запроса.

**Вопрос о самом диалоге (S1-M12).** «Напомни: о чём был мой самый первый
вопрос и что ты тогда назвал первым этапом?» — классификатор пометил
`needs_history`, ответ собран из полной истории и памяти (первый вопрос — RAG и
пайплайн, первый этап — индексация/чанки), поиск по базе не выполнялся: это
единственный тип вопросов, где RAG не нужен конструктивно.

**Вне-корпусные вопросы (S1-M09, S2-M09).** Медовик и Лига чемпионов: макс.
скор реранкера 0.0 → контекст пуст → детерминированное «не знаю» + просьба
уточнить, генерация не вызывается вовсе. В отладочном прогоне был и случай,
когда один чанк на граничной оценке прошёл порог, а модель **сама** ответила
«вне базы знаний, не могу ответить» — теперь такой ответ детерминированно
детектируется (маркеры отказа + нет источников/цитат) и заменяется
каноническим отказом (ветка `model_no_answer`, как в day-4).

**Термин переживает окно истории (S1-M04, S2-M06).** «Что такое эмбеддинг?» →
ответ (числовой вектор смысла) усечённо лёг в глоссарий памяти; «что за
заголовок Mcp-Session-Id» → аналогично. В финальных проверках терминов
(`термины ∋ …`) глоссарий подтверждается детерминированно.

## Выводы

- **История диалога и RAG связываются через rewrite.** Follow-up с
  местоимениями («перееду с ним на VPS», «для моей ситуации») бесполезен как
  поисковый запрос — rewrite с окном истории и памятью задачи делает его
  самодостаточным, и поиск находит ровно нужные чанки (11/11 rewrite-чеков).
  Реранкер при этом судит уже самодостаточный запрос, а не сырой follow-up.
- **Память задачи — дешёвый способ «дальнобойного» контекста.** Окно истории
  видит 4–6 ходов, а условие «сервер на одной машине» (сообщение №2) работает
  в ответе на №10 — потому что живёт не в истории, а в памяти, и попадает
  сразу в три места: rewrite, генерацию и проверки. Это ровно стратегия
  «вынесенные факты» из week-2/day-5, применённая к задаче чата.
- **Извлечение памяти — до ответа, а не после.** Ограничение «коротко и без
  кода» из текущего сообщения действует уже на текущий ответ (12/12 ответов
  без кода после ввода правила). Merge детерминированный: LLM только
  предлагает добавления, применяет их код с дедупликацией — память нельзя
  «переписать» неудачной генерацией.
- **Классификатор сообщения — четвёртая ветка пайплайна.** Мета-сообщения
  (правила, цель) не должны попадать в RAG — иначе вместо «Принято» выйдет
  «не знаю». Вопросы о самом диалоге — наоборот, не должны попадать в базу.
  Оба случая решаются одним LLM-вызовом извлечения памяти (`meta_only`,
  `needs_history`), который и так нужен. Граничный случай из отладочного
  прогона — модель сама честно отказалась при граничном скоре реранкера —
  закрыт детерминированной детекцией «ответа-отказа» (маркеры + нет
  источников) с заменой на канонический отказ.
- **Структурная дисциплина day-4 не дала ни одной подделки.** Все 39 ссылок и
  46 цитат двух сценариев валидны, 0 unsupported: в чате с историей и памятью
  соблазн «ответить красиво из контекста диалога» выше, чем в одиночном
  запросе — но строгий JSON с chunk_id, валидатор цитат и faithfulness-судья
  держат планку и здесь. Судья честно ставит `partial`, когда модель
  добавляет факты за пределами процитированного (4 случая — все с верными
  ответами по чанкам).
- **Цена вопроса:** 115 LLM-вызовов на 26 сообщений (~4,4 на сообщение:
  память + rewrite + реранк + генерация + судья; отказы и мета — дешевле).
  Два сетевых сбоя во время прогонов (DNS) закрыты ретраями с паузами
  3/10/30 с — длинные сессии живучее коротких одиночных запросов.
