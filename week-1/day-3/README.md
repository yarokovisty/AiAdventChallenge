# Week 1 · Day 3 — Четыре способа рассуждения через API

## Условие задания

Взять одну задачу и решить её через API **четырьмя способами рассуждения**:

1. прямой ответ без инструкций;
2. инструкция «решай пошагово»;
3. модель сама составляет промпт, а затем им решает;
4. группа экспертов (аналитик / инженер / критик).

Сравнить: отличаются ли ответы, какой способ точнее.

## Подход

Проект day-2 (Kotlin + Jetpack Compose, Z.ai GLM-5.3) скопирован в [LLMDemo/](LLMDemo/) и переделан. День 2 оставлен без изменений.

Приложение — **стенд сравнения способов рассуждения**: пользователь вводит задачу один раз и жмёт «Решить». Одна и та же задача решается **четырьмя способами подряд**, результаты показываются карточками. У многошаговых способов промежуточные шаги (сгенерированный промпт, вклад каждого эксперта) скрыты в раскрывающихся блоках — чтобы карточка оставалась чистой для видео, но детали были под рукой.

Для наглядности добавлены две вещи:

- **Авто-сверка с эталоном.** Из финального ответа вытаскивается последнее число и сравнивается с эталонным ответом. Карточка подсвечивается зелёным (`✓`) при совпадении и показывает `✗ N ≠ эталон` при расхождении — на видео сразу видно, кто прав.
- **Режим статистики стабильности.** Кнопки `×3 / ×5 / ×10` прогоняют каждый способ несколько раз и показывают карточку со списком ответов по прогонам и счётом «K / N верно». Именно так и собрана таблица результатов ниже — только теперь прямо в приложении.

### Выбор задачи

Нужна была задача с **одним проверяемым ответом**, где интуитивный/паттерновый ответ модели ошибается, а аккуратное рассуждение — помогает. Классические «ловушки» (бита и мяч, улитка на стене, возраст брата) GLM-5.3 решает верно даже напрямую — он для них слишком силён.

Зато у LLM есть устойчивое слабое место — **подсчёт букв**: из-за токенизации модель «не видит» отдельные символы и считает их на глаз. Поэтому задача:

> **Сколько раз буква «р» встречается во фразе: «Карл у Клары украл кораллы, а Клара у Карла украла кларнет»?**
>
> **Правильный ответ: 8** (проверено посимвольным перечислением).

Прямой ответ на неё не просто ошибается, а **нестабилен** (в прогонах: 7, 9, 7, 9) — наглядно для видео.

### Как реализован каждый способ

Все четыре способа получают одинаковую задачу. Общий для всех нюанс — `thinking: disabled` (см. ниже).

| # | Способ | Вызовов API | Что делает |
|---|--------|:---:|---|
| 1 | Прямой ответ | 1 | Задача уходит как есть, без инструкций. |
| 2 | Пошагово | 1 | + system-инструкция «решай пошагово, в конце строка `Ответ: …`». |
| 3 | Самопромпт | 2 | Вызов A: модель составляет оптимальный промпт для задачи (не решая её). Вызов B: решает уже этим промптом. |
| 4 | Группа экспертов | 3 | Цепочка: **аналитик** (разбирает задачу) → **инженер** (решает, видя разбор) → **критик** (проверяет и выдаёт финал). Каждый видит контекст предыдущих. |

### Ключевой нюанс: `thinking: disabled` обязателен

GLM-5.3 — reasoning-модель (урок из [day-2](../day-2/)). Если оставить встроенное «размышление» включённым, то **даже «прямой ответ» тайно получает цепочку рассуждений**, и разница между четырьмя способами исчезает — сравнивать будет нечего. Поэтому во всех запросах стоит `thinking: {"type": "disabled"}` — рассуждение остаётся только то, что задаёт сам способ.

## Ключевые изменения в коде относительно day-2

- `data/ReasoningStrategy.kt` (вместо `ControlConfig.kt`) — enum из 4 способов + модель результата `StrategyResult` (финальный ответ + промежуточные шаги + токены) + сама задача и эталонный ответ.
- `data/DataRepository.kt` — низкоуровневый `chat(messages)` (с `thinking=disabled`) + оркестратор `solve(problem, strategy)`, который для каждого способа выстраивает свою цепочку вызовов.
- `data/AnswerCheck.kt` — эвристика извлечения итогового ответа и сверка с эталоном. Итог ищется по убыванию надёжности: маркер «Ответ: N» → «N раз» → последнее число. (Простое «последнее число» не годится: у самопромпта ответ часто заканчивается перечислением «… — кларнет — 1», и последняя цифра — не итог.)
- `ui/main/MainScreenViewModel.kt` — `runComparison()` (один прогон, полные карточки) и `runStability(times)` (прогон каждого способа N раз со сбором статистики).
- `ui/main/MainScreen.kt` — ввод задачи, эталон, кнопки «Решить» и `×3/×5/×10`, карточки результата с подсветкой совпадения, раскрывающимися шагами и токенами + карточки статистики.

## Результаты сравнения

> Задача: подсчёт буквы «р» (выше). Модель `glm-5.3`, `thinking=disabled`. Правильный ответ — **8**.

Прогнал каждый способ **4 раза** (ответы недетерминированы):

| Способ | Ответы по прогонам | Верных | Токенов (всего) |
|--------|--------------------|:------:|:---------------:|
| 1. Прямой ответ | 9, 7, 7, 9 | **0 / 4** | ~255 |
| 2. Пошагово | 9, 8, 5, 9 | 1 / 4 | ~320 |
| 3. Самопромпт | 8, 8, 8, 8 | **4 / 4** | ~1200 |
| 4. Группа экспертов | 6, 8, 8, 8 | 3 / 4 | ~2320 |

### Что видно по каждому способу

- **Прямой ответ** — всегда мимо (7–9) и нестабилен. Модель считает буквы «на глаз» по токенам, не перечисляя их. Самый дешёвый и самый ненадёжный.
- **Пошагово** — перечисляет буквы по словам правильно (по 1 на слово), но ошибается на **финальном сложении**: выписывает лишнюю единицу и получает 9 вместо 8, либо наоборот теряет слагаемое (5). Процесс лучше, но арифметика всё ещё хромает.
- **Самопромпт** — единственный стабильный: 8 во всех прогонах. Причина в том, *какой* промпт модель себе сгенерировала: она сама добавила шаг «перед финальным ответом перепроверь каждое слово посимвольно». Именно этот self-check и ловил ошибки.
- **Группа экспертов** — обычно верно (8), но один раз выдала 6: **аналитик внёс ошибку** (заявил, что в «кораллы» две «р», а в «Клара»/«кларнет» нет «р»), инженер частично исправил, но ложную часть принял, а критик её **подтвердил**. Ошибка прошла по всей цепочке. Самый дорогой способ (3 вызова).

### Выводы

- **Ответы отличаются** — и по значению, и по стабильности. Способ рассуждения прямо влияет на точность.
- **Точнее всего — самопромпт**, и не из-за «магии»: модель сама заложила в промпт явную перепроверку, а self-verification — главный рычаг точности на задачах такого типа.
- **«Решай пошагово» помогает процессу, но не гарантирует результат** — декомпозиция верная, а финальная арифметика всё равно плывёт.
- **Больше агентов ≠ точнее.** Цепочка экспертов может *усилить* раннюю ошибку: если аналитик ошибся, инженер и критик склонны ему поверить (каскад ошибок). Многоролевая схема выигрывает только когда критик реально перепроверяет с нуля, а не доверяет предыдущим.
- **Точность стоит токенов:** прямой ответ ~255 токенов, эксперты ~2320 — почти в 9 раз дороже. Самопромпт даёт лучшую точность за среднюю цену (~1200).

## Как запустить

1. Открыть `LLMDemo/` в Android Studio (ключ API берётся из `LLMDemo/.env`, поле `API_KEY`).
2. Запустить на эмуляторе/устройстве, ввести задачу (по умолчанию — задача про букву «р»), нажать **«Решить»**.
3. Приложение последовательно решит задачу четырьмя способами и покажет карточки; карточка подсвечивается зелёным при совпадении с эталоном. Промежуточные шаги (сгенерированный промпт, разбор аналитика, решение инженера) раскрываются по тапу.
4. Кнопки **`×3 / ×5 / ×10`** прогоняют каждый способ несколько раз и показывают статистику стабильности (сколько прогонов из N дали верный ответ).

> Из-за недетерминированности ответов числа при живом запуске могут отличаться от таблицы выше — это часть демонстрации (особенно для способов 1, 2, 4).
