# Week 1 · Day 2 — Контроль ответа LLM через API

## Условие задания

Взять проект из [day-1](../day-1/) и доработать: отправить **один и тот же запрос** с разным уровнем контроля ответа через API.

Нужно продемонстрировать три техники контроля:
1. **Явное описание формата ответа**
2. **Ограничение на длину ответа**
3. **Условие завершения** (stop sequence / явная инструкция)

И сравнить ответы: **без ограничений vs с ограничениями**.

## Подход

Проект day-1 (Kotlin + Jetpack Compose, Z.ai GLM-5.3) скопирован в [LLMDemo/](LLMDemo/) и доработан. Day-1 оставлен без изменений.

Вместо чата приложение теперь — **стенд сравнения**: пользователь вводит запрос один раз и жмёт «Сравнить». Один и тот же запрос уходит в API **в 5 конфигурациях**, результаты показываются карточками с метаданными (`finish_reason`, число токенов).

### Параметры контроля Z.ai API

API Z.ai совместим с OpenAI-форматом. Используемые рычаги:

| Техника из задания | Параметр запроса |
|---|---|
| Явное описание формата | `response_format: {"type":"json_object"}` + system-инструкция с описанием структуры |
| Ограничение длины | `max_tokens` (1–131072) |
| Условие завершения | `stop` (массив строк, до 4) + явная инструкция в промпте |

В ответе анализируем `finish_reason` (`stop` — модель завершила сама / по стоп-строке, `length` — упёрлась в `max_tokens`) и `usage.completion_tokens`.

### 5 конфигураций

| # | Вариант | Параметры |
|---|---------|-----------|
| 1 | Baseline — без ограничений | — |
| 2 | Контроль формата | `response_format=json_object` + system-описание полей JSON |
| 3 | Контроль длины | `max_tokens=64` |
| 4 | Условие завершения | `stop=["[STOP]"]` + инструкция завершить маркером |
| 5 | Всё вместе | формат (инструкция) + `max_tokens=120` + `stop=["[STOP]"]` |

## Ключевые изменения в коде относительно day-1

- `data/ControlConfig.kt` — новая модель конфигурации контроля + `AskResult` (content + `finish_reason` + токены) + список из 5 конфигов.
- `data/DataRepository.kt` — `ask(prompt, config)` собирает тело запроса с опциональными `max_tokens` / `stop` / `response_format` и system-сообщением; парсит `finish_reason` и `usage`.
- `ui/main/MainScreenViewModel.kt` — по одному вводу последовательно отправляет 5 запросов, собирает `VariantResult`.
- `ui/main/MainScreen.kt` — поле ввода, кнопка «Сравнить», карточки результатов с подписью параметров и метаданными.
- Удалён `data/Message.kt` (старая модель чата не нужна).

## Важный нюанс: GLM-5.3 — reasoning-модель

При первом прогоне ответы в вариантах с `max_tokens`/`stop` приходили **пустыми**. Причина: у GLM-5.3 по умолчанию включено «размышление» (reasoning). Бюджет `max_tokens` и стоп-строки применяются сначала к скрытой цепочке рассуждений, а не к видимому ответу. Проверка сырого ответа API:

```json
"message": {
  "content": "",
  "reasoning_content": "The user is asking about advantages of Kotlin... Let me think..."
},
"usage": { "completion_tokens": 64, "completion_tokens_details": { "reasoning_tokens": 60 } }
```

То есть `max_tokens=64` целиком ушли в reasoning, а `content` остался пустым.

**Решение:** во все запросы добавлен `thinking: {"type": "disabled"}` — тогда параметры контроля применяются именно к видимому ответу. Это ключевой урок задания: на reasoning-моделях контроль длины/завершения нужно учитывать вместе с рассуждением.

## Результаты сравнения

> Запрос: `Расскажи о преимуществах Kotlin для Android-разработки.` (модель `glm-5.3`, `thinking=disabled`)

| # | Вариант | finish_reason | Токенов (ответ) | Что видно |
|---|---------|---------------|-----------------|-----------|
| 1 | Baseline — без ограничений | `stop` | ~546 | Самый длинный ответ: markdown-разметка, заголовки, примеры кода. Модель сама решает объём и формат. |
| 2 | Формат (JSON) | `stop` | ~150 | Строгий машиночитаемый JSON `{"summary": "...", "advantages": ["...", ...]}`. Ни markdown, ни пояснений вне JSON. |
| 3 | Длина (`max_tokens=64`) | **`length`** | 64 | Ответ **обрывается на полуслове** («…все новые библиотеки и примеры код»). Экономия токенов ценой полноты. |
| 4 | Stop (`[STOP]`) | `stop` | ~782 | Полный ответ, завершённый по маркеру. Сам `[STOP]` в текст **не попадает** (стоп-строка отсекается). Предсказуемая граница вместо естественного конца. |
| 5 | Всё вместе | **`length`** | 120 | Нумерованный список (формат задан инструкцией), но обрыв по `max_tokens=120` раньше, чем модель дошла до `[STOP]`. |

### Выводы

- **Без ограничений** модель даёт максимально полный ответ, но его длина и формат непредсказуемы — неудобно для программной обработки.
- **`response_format=json_object` + описание полей** даёт стабильно парсящийся JSON — лучший способ, когда ответ нужен коду, а не человеку.
- **`max_tokens`** жёстко режет длину: `finish_reason` становится `length`, а ответ может оборваться на полуслове. Это контроль стоимости/объёма, но не смысловой завершённости.
- **`stop` + явная инструкция** дают *смысловую* границу: модель заканчивает мысль и ставит маркер, генерация останавливается, маркер в ответ не попадает (`finish_reason=stop`).
- **При комбинации ограничений срабатывает самое строгое:** в варианте 5 лимит `max_tokens=120` сработал раньше стоп-маркера, поэтому `finish_reason=length`.
- `finish_reason` — главный индикатор того, *почему* ответ закончился: `stop` (модель/стоп-строка завершили естественно) vs `length` (упёрлись в лимит).

## Как запустить

1. Открыть `LLMDemo/` в Android Studio (ключ API берётся из `LLMDemo/.env`, поле `API_KEY`).
2. Запустить на эмуляторе/устройстве, ввести запрос, нажать **«Сравнить»** — приложение последовательно отправит 5 запросов и покажет карточки с ответами, `finish_reason` и числом токенов.
