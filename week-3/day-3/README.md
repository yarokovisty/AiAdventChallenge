# Week 3 · Day 3 — Состояние задачи как конечный автомат (FSM)

## Условие задания

Реализовать состояние задачи как **конечный автомат**:

- **этап задачи**;
- **текущий шаг**;
- **ожидаемое действие**.

Пример состояний: `planning → execution → validation → done`.

Проверить:

- **паузу** на любом этапе;
- **продолжение** без повторных объяснений.

**Результат:** агент с формализованным состоянием задачи.

---

## Что сделано

За основу взята реализация из [Week 3 · Day 2](../day-2/) — самая полная версия
агента (три слоя памяти + персонализация), которая, в свою очередь, наследует
весь функционал week-2. Поверх неё добавлен **новый формализованный слой —
состояние задачи как конечный автомат**.

Идейно это продолжение *рабочей памяти* из Day 1 (там была «задача + заметки»
без формализации). Теперь жизненный цикл задачи описан явным автоматом:

```
planning ──► execution ──► validation ──► done
                  ▲             │
                  └─────────────┘  (возврат на доработку)
```

Пауза — это **не отдельный этап**, а флаг поверх любого этапа: задачу можно
приостановить на planning/execution/validation и продолжить с того же шага.

Ключевая идея: **всё состояние автомата сохраняется на диск и уходит в системный
промпт каждого запроса**. Поэтому после паузы или даже полного перезапуска
приложения агент продолжает с того же шага — пользователю не нужно заново
объяснять контекст.

| Что хранит слой | Файл во `filesDir` | Как попадает в запрос |
|-----------------|--------------------|-----------------------|
| **Состояние задачи (FSM)**: этап / шаг / ожидаемое действие / пауза / журнал | `task_state.json` | блок «Состояние задачи» в system-prompt |

---

## Три формализованных поля (ровно то, что просило задание)

| Поле | Смысл |
|------|-------|
| `stage` | **этап задачи** — состояние автомата (`planning/execution/validation/done`) |
| `currentStep` | **текущий шаг** внутри этапа |
| `expectedAction` | **ожидаемое действие** агента на этом шаге |

Плюс к этому `isPaused` (пауза на любом этапе) и `log` (журнал переходов) — они и
делают автомат пригодным к паузе/продолжению.

---

## Архитектура: FSM вынесен в чистое ядро

Вся логика переходов — в одном чистом месте `domain/task/`:

```
domain/task/
  TaskStage.kt           # enum этапов + порядок + латинские ключи
  TaskState.kt           # неизменяемый снимок: goal, stage, step, action, isPaused, log
  TaskStateMachine.kt    # ЧИСТЫЙ автомат: таблица переходов + start/advance/rollback/pause/resume
  TaskStateRepository.kt # порт хранилища (load/save/clear)

data/task/
  StoredTaskState.kt         # @Serializable DTO + мапперы (этап хранится slug'ом)
  JsonTaskStateRepository.kt # реализация на task_state.json
```

`TaskStateMachine` не хранит состояние и не делает ввод-вывод: принимает
`TaskState` → возвращает новый. **Разрешённые переходы заданы таблицей** —
именно это формализует жизненный цикл:

```kotlin
private val TRANSITIONS: Map<TaskStage, Set<TaskStage>> = mapOf(
    PLANNING   to setOf(EXECUTION),
    EXECUTION  to setOf(VALIDATION),
    VALIDATION to setOf(DONE, EXECUTION),  // готово или возврат на доработку
    DONE       to emptySet(),
)
```

Недопустимый переход — это исключение, а не молчаливый баг. У каждого этапа есть
дефолтные «шаг» и «ожидаемое действие», которые подставляются при переходе.

Как и в прошлые дни, доменная модель — чистый Kotlin (без `@Serializable`);
формат хранения живёт в DTO слоя data.

## Как состояние попадает в запрос

Автомат едет в том же `MemoryContext`, что и память с профилем, и собирается в
системный промпт отдельным блоком (`ChatAgent.appendTaskState`):

```
# Состояние задачи (конечный автомат — ориентируйся на него)
Цель задачи: Implement a Kotlin list sorting function
Этапы: Планирование → Выполнение → Проверка → Готово
Текущий этап: Выполнение (execution)
Текущий шаг: Выполнение шагов плана
Ожидаемое действие: Выполняй шаги плана по порядку, фиксируй промежуточный результат.
Журнал задачи:
- Задача начата на этапе «Планирование».
- Переход: Планирование → Выполнение.
Веди себя соответственно текущему этапу. При продолжении не проси повторять
уже известный контекст — он весь приведён выше.
```

Поток данных (продолжение схемы прошлых дней):

```
UI (панель задачи) ── StartTask / AdvanceStage / PauseTask / ResumeTask ──► ChatViewModel
                                                      │  TaskStateMachine (чистые переходы)
                                                      │  taskState.save(...) → task_state.json
ask(query, history, MemoryContext(..., task)) ─► ChatAgent ─► LLM
```

## Живой прогон (эмулятор `emulator-5554`, модель `glm-4.6`)

Задача: **`Implement a Kotlin list sorting function`** (цель задана латиницей —
`adb` не вводит кириллицу; ответы агент даёт по-русски из system-prompt).

### 1. Этап `planning` → агент **планирует**

Запрос был минимальным — **`Let's begin. What do we do now?`**, задачу я не
пересказывал. Агент взял цель из автомата и, согласно этапу планирования, выдал
**план**:

> Ярослав, план такой:
> 1. Определить сигнатуру: `fun <T : Comparable<T>> List<T>.sortedCustom(): List<T>`…
> 2. Выбрать алгоритм — для задачи хватит merge sort (O(n log n), стабильный).
> 3. Реализовать чистую функцию без мутации исходного списка.
> 4. Проверить: пустой список, один элемент, дубликаты, уже отсортированный.
>
> Подтверди или уточни требования…

(Имя «Ярослав» — из долговременной памяти Day 1; стиль технолога — из профиля
«Senior-разработчик» Day 2. Слои работают вместе.)

### 2. Переход на `execution` → агент **выполняет**

Кнопка «Далее →» перевела автомат `planning → execution`. На сообщение
**`Continue.`** агент перешёл к реализации — написал функцию merge sort и
зафиксировал промежуточный результат: «базовая версия готова. Следующий шаг —
проверки…».

### 3. Пауза на этапе + **перезапуск приложения**

Задача поставлена на паузу на этапе `execution` (кнопка «⏸ Пауза»). Затем
приложение **полностью убито** (`am force-stop`) и запущено заново. Состояние
автомата восстановилось с диска полностью:

- шапка: «Задача: Выполнение ⏸»;
- этап `execution`, тот же шаг и ожидаемое действие;
- журнал цел: *старт → переход Планирование→Выполнение → пауза на Выполнении*.

Это и есть **пауза на любом этапе**: состояние заморожено, переходы заблокированы
и снимок пережил перезапуск.

### 4. Продолжение **без повторных объяснений** (изолированно от истории)

Чтобы доказать, что продолжение держится именно на автомате, а не на истории
диалога, я **очистил диалог** (стёр краткосрочную память) и возобновил задачу.
При **пустой истории** одно сообщение — **`Continue.`** — и агент продолжил:

> **Продолжаю выполнение: реализация сортировки списка на Kotlin.**
> ```kotlin
> fun <T : Comparable<T>> List<T>.sortAscending(): List<T> = sorted()
> ```
> Результат: функция реализована — используется стандартный `sorted()`
> (tim sort, O(n log n)), иммутабельно, без побочных эффектов.
> **Следующий шаг — проверка.**

Агент знает **задачу, этап и что делать дальше** только из состояния автомата в
system-prompt — истории чата не было вовсе. Это и есть «продолжение без повторных
объяснений».

## Про семантику паузы (честное наблюдение)

Пауза **авторитетна на уровне автомата**: состояние замораживается, переходы
между этапами запрещены (`TaskStateMachine` бросает исключение на переход во
время паузы), снимок персистентен. Системный промпт при этом *информирует*
агента, что задача на паузе и продолжать нужно с того же шага.

На практике GLM-4.6 трактует это как мягкую подсказку: при явной команде
«Continue.» модель всё равно продолжает. Поэтому «пауза» в этой реализации — это
**механизм состояния** (заморозка + персистентность + отсутствие переходов), а не
принудительное молчание модели. Именно в таком виде пауза и продемонстрирована:
через заморозку и восстановление состояния после перезапуска.

## Как запустить

1. Положить ключ в `AgentDemo/.env`: `API_KEY=<ваш_ключ_Z.ai>`.
2. Собрать: `./gradlew :app:assembleDebug`.
3. Установить и запустить `com.example.agentdemo`.
4. Иконка «чеклист» в шапке → панель задачи. Начать задачу, нажимать «Далее →»
   по этапам, поставить «⏸ Пауза», при желании закрыть и заново открыть приложение
   (состояние восстановится), «▶ Продолжить» и прислать «Continue.» — агент
   продолжит с того же шага.

## Выводы

- Конечный автомат лёг на архитектуру как **ещё один порт + хранилище + блок в
  system-prompt**, без переписывания агента — ровно как профиль в Day 2.
- **Вся логика переходов изолирована** в чистом `TaskStateMachine` с явной
  таблицей переходов — состояние задачи стало формальным и проверяемым.
- Персистентность состояния = **пауза, пережившая перезапуск**: задачу можно
  бросить на любом этапе и вернуться к ней позже.
- Формализованное состояние в каждом запросе = **продолжение без повторных
  объяснений**: даже при пустой истории диалога агент продолжает задачу с того
  же шага, зная этап и ожидаемое действие.
