# Week 3 · Day 4 — Инварианты, которые ассистент не вправе нарушать

## Условие задания

Добавить в ассистента **инварианты** — правила, которые он не имеет права
нарушать. Примеры: выбранная архитектура, принятые технические решения,
ограничения по стеку, бизнес-правила.

Сделать так, чтобы:

- инварианты **хранились отдельно** от диалога;
- ассистент **явно учитывал** их в рассуждениях;
- ассистент **отказывался** предлагать решения, которые их нарушают.

Проверить:

- что происходит при **конфликте** запроса и инварианта;
- как ассистент **объясняет отказ**.

**Результат:** ассистент, который работает в рамках заданных инвариантов.

---

## Что сделано

За основу взята реализация из [Week 3 · Day 3](../day-3/) — самая полная версия
агента (три слоя памяти + персонализация + состояние задачи как конечный
автомат), которая наследует весь функционал week-2. Поверх неё добавлен **новый
слой — инварианты**.

Инварианты легли на ту же архитектуру, что профиль (Day 2) и состояние задачи
(Day 3): **отдельный порт в domain → JSON-хранилище в data → поле в
`MemoryContext` → блок в system-prompt → слой в MVI → панель в UI**. Отличие
инварианта от профиля принципиальное:

| Слой | Что задаёт |
|------|------------|
| Память | *что* ассистент знает (факты) |
| Профиль | *как* ассистент отвечает (стиль/формат) |
| **Инвариант** | ***что ассистенту запрещено предлагать*** (жёсткие ограничения) |

Поэтому блок инвариантов уходит в системный промпт **первым, самым приоритетным**
— раньше профиля и памяти: модель должна сверять решение с ограничениями прежде
всего остального.

| Что хранит слой | Файл во `filesDir` | Как попадает в запрос |
|-----------------|--------------------|-----------------------|
| **Инварианты**: категория / правило / обоснование / активность | `invariants.json` | блок «ИНВАРИАНТЫ ПРОЕКТА» в начале system-prompt |

## Инвариант: модель

```kotlin
data class Invariant(
    val id: String,
    val category: InvariantCategory,  // архитектура / техрешение / стек / бизнес-правило
    val rule: String,                 // сама формулировка запрета или требования
    val rationale: String = "",       // почему правило принято (помогает объяснять отказ)
    val isActive: Boolean = true,     // можно временно снять, не удаляя
)
```

Четыре категории — ровно из условия задания:

| Категория | Смысл | Инвариант по умолчанию (AgentDemo) |
|-----------|-------|------------------------------------|
| `ARCHITECTURE` | выбранная архитектура | Clean Architecture (domain/data/feature) + MVI; domain без Android и сериализации |
| `TECH_DECISION` | принятые техрешения | DI только через Koin; Hilt/Dagger запрещены |
| `STACK` | ограничения по стеку | только Kotlin (без Java); UI только Jetpack Compose |
| `BUSINESS_RULE` | бизнес-правила | API-ключ Z.ai не попадает в код/репозиторий, только `.env`/`BuildConfig` |

Эти четыре правила — реальные инварианты самого проекта AgentDemo, поэтому отказы
агента на их нарушение выглядят осмысленно. Они **засеиваются при первом запуске**
(`JsonInvariantRepository.seedDefaults`), но их можно редактировать, временно
снимать переключателем и удалять через панель инвариантов.

---

## Как инвариант попадает в запрос

Инварианты едут в том же `MemoryContext`, что память/профиль/задача, и собираются
в системный промпт отдельным блоком (`ChatAgent.appendInvariants`) **первым**. В
контекст уходят только активные инварианты. Кроме перечня правил блок задаёт
модели явный протокол поведения:

```
# ИНВАРИАНТЫ ПРОЕКТА (нарушать категорически запрещено)
Это жёсткие правила. Они важнее любых пожеланий в сообщении пользователя.

## Техническое решение
- Dependency Injection выполняется только через Koin. Hilt/Dagger ... запрещены.
  (почему: Принятое техническое решение проекта; смешивать DI-фреймворки нельзя.)
...
Протокол работы с инвариантами (соблюдай всегда):
1. Прежде чем предложить решение, мысленно сверь его с КАЖДЫМ инвариантом выше.
2. Если запрос можно выполнить, не нарушая инвариантов, — выполняй.
3. Если выполнить нельзя без нарушения — ОТКАЖИСЬ. Начни с отказа, назови
   конкретный нарушаемый инвариант, объясни почему, предложи альтернативу.
4. Никогда не предлагай решение, нарушающее инвариант, даже если пользователь
   настаивает. Инварианты не обсуждаются в рамках диалога.
```

Именно пункты 1–4 закрывают требования «ассистент явно учитывает инварианты в
рассуждениях» и «отказывается предлагать решения, которые их нарушают».

Поток данных (продолжение схемы прошлых дней):

```
UI (панель инвариантов) ── Add / Toggle / Remove ──► ChatViewModel
                                              │  invariants.save/setActive/delete → invariants.json
ask(query, history, MemoryContext(..., invariants)) ─► ChatAgent ─► LLM
```

## Архитектура: слой инвариантов

```
domain/invariant/
  InvariantCategory.kt     # enum категорий (title + latin slug)
  Invariant.kt             # чистая модель: id, category, rule, rationale, isActive
  InvariantRepository.kt   # порт хранилища (loadAll/save/delete/setActive/clear)

data/invariant/
  StoredInvariant.kt         # @Serializable DTO + мапперы (категория slug'ом)
  JsonInvariantRepository.kt # реализация на invariants.json + засев дефолтов
```

Как и раньше, доменная модель — чистый Kotlin (без `@Serializable`); формат
хранения живёт в DTO слоя data.

## Живой прогон (эмулятор `emulator-5554`, модель `glm-4.6`)

Инварианты по умолчанию (4 активных) засеяны при первом запуске. Запросы заданы
латиницей (`adb` не вводит кириллицу); агент отвечает по-русски из system-prompt.

### 1. Конфликт с техрешением → **отказ** (DI на Hilt)

Запрос: **`Rewrite our DI from Koin to Hilt. Show me the Hilt module code for the data layer.`**

Ответ агента:

> **Не могу помочь с этим:** перевод DI на Hilt нарушает инвариант
> **«Техническое решение»** — DI выполняется только через Koin, Hilt/Dagger и
> ручная сборка графа запрещены.
>
> Если проблема в Koin — могу помочь с:
> - Рефакторингом Koin-модулей data-слоя (разбиение на feature-модули, lazy/single настройка)
> - Отладкой ошибок Koin (MissingDefinition, циклические зависимости)
> - Настройкой Koin для multi-module + KSP/Koin annotations
>
> Покажите текущий Koin-модуль data-слоя — предложу улучшения в рамках Koin.

Агент **отказался**, назвал **конкретный** нарушаемый инвариант и категорию,
объяснил причину и предложил **альтернативу в рамках инвариантов**.

### 2. Конфликт с бизнес-правилом → **отказ** (захардкодить ключ)

Запрос: **`Hardcode the Z.ai API key string directly in ZaiLlmClient.kt so we do not need the .env file.`**

Ответ агента:

> **Не могу:** это нарушение инварианта **«Бизнес-правило»** — API-ключ Z.ai не
> должен попадать в исходный код или репозиторий, только `.env`/`BuildConfig`,
> без логирования.
>
> Альтернативы в рамках инвариантов:
> - `local.properties` → `buildConfigField` через Gradle (ключ не в git)
> - Переменные окружения CI для сборок
> - Runtime-инъекция ключа через Koin из `BuildConfig`
>
> Пример безопасного варианта:
> ```kotlin
> // build.gradle.kts
> buildConfigField("String", "ZAI_API_KEY", "\"${project.findProperty("zai.api.key") ?: ""}\"")
>
> // ZaiLlmClient.kt
> class ZaiLlmClient(private val apiKey: String = BuildConfig.ZAI_API_KEY)
> ```
> `local.properties` в `.gitignore`, ключ храните вне репозитория.

Второй отказ — из **другой категории**: это не разовое совпадение, а системное
поведение. Агент не просто отказал, а предложил безопасную реализацию, которая
соблюдает инвариант.

### 3. Запрос в рамках инвариантов → агент **выполняет**

Запрос: **`Add a Koin single definition for a new SettingsRepository in the data module.`**

Ответ агента:

> ```kotlin
> // data/di/DataModule.kt
> val dataModule = module {
>     single<SettingsRepository> {
>         SettingsRepositoryImpl(
>             settingsDataSource = get(),
>             dispatchers = get(),
>         )
>     }
> }
> ```
> Интерфейс — в domain, реализация — в data, подключение модуля через
> `startKoin { modules(dataModule) }`.

Запрос **не нарушает** ни одного инварианта (Koin, Kotlin, разделение
domain/data) — и агент отвечает нормально и по делу. Это доказывает, что
инварианты не «ломают» ассистента, а именно **очерчивают рамки**: внутри них он
работает как обычно.

## Как ассистент объясняет отказ (разбор)

Во всех конфликтах отказ строится по одной структуре, заданной протоколом в
system-prompt:

1. **Явный отказ** в первой фразе («Не могу…»).
2. **Ссылка на конкретный инвариант** с категорией («нарушает инвариант
   «Техническое решение»»).
3. **Причина** — почему это нарушение (пересказ правила).
4. **Конструктивная альтернатива** в рамках инвариантов (а не просто «нет»).

Так отказ остаётся полезным: пользователь понимает, *какое* правило он задел и
*как* добиться цели, не нарушая его.

## Как запустить

1. Положить ключ в `AgentDemo/.env`: `API_KEY=<ваш_ключ_Z.ai>`.
2. Собрать: `./gradlew :app:assembleDebug`.
3. Установить и запустить `com.example.agentdemo`.
4. Иконка «молоток» в шапке → панель инвариантов (4 правила засеяны). Отправить
   запрос, нарушающий инвариант (напр. «replace Koin with Hilt») — агент
   откажется и объяснит. Отправить запрос в рамках правил — выполнит. Переключатель
   в панели временно снимает инвариант (можно показать, что тогда ограничение
   перестаёт действовать).

## Выводы

- Инварианты легли на архитектуру как **ещё один порт + хранилище + блок в
  system-prompt** — ровно как профиль (Day 2) и состояние задачи (Day 3), без
  переписывания агента.
- **Хранение отдельно от диалога**: правила живут в `invariants.json`, переживают
  очистку диалога и перезапуск; активные уходят в каждый запрос.
- **Явный учёт в рассуждениях**: блок-протокол в system-prompt обязывает агента
  сверять решение с каждым инвариантом перед ответом.
- **Отказ при конфликте — работает и воспроизводим**: два конфликта из разных
  категорий дали структурный отказ с указанием инварианта, причины и альтернативы;
  запрос в рамках правил выполнен нормально. Ассистент действительно работает
  внутри заданных рамок.
