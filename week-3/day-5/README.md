# Week 3 · Day 5 — Явные переходы между состояниями задачи

## Условие задания

Реализовать **явные переходы** между состояниями задачи. Сделать так, чтобы:

- у задачи были **допустимые состояния**;
- были **разрешённые переходы** между ними;
- ассистент **не мог «перепрыгнуть» этап**.

Примеры:

- нельзя делать реализацию **до утверждённого плана**;
- нельзя делать финал **без валидации**.

Проверить:

- попытки перейти в **недопустимое состояние**;
- **реакцию** ассистента;
- **корректность продолжения после паузы**.

**Результат:** ассистент с контролируемым жизненным циклом задачи.

---

## Что сделано

За основу взята реализация из [Week 3 · Day 4](../day-4/) — самая полная версия
агента (три слоя памяти + персонализация + состояние задачи как конечный автомат +
инварианты). В Day 3 уже был конечный автомат задачи (`planning → execution →
validation → done`) с таблицей разрешённых переходов. **Day 5 усиливает именно
переходы**: добавляет к ним **шлюзы (guards)** и делает отказ на недопустимом
переходе явным и видимым.

### Ключевое отличие от Day 3: переходы со шлюзами

В Day 3 переход `planning → execution` был **безусловным** (нажал «Далее» —
перешёл). Задание Day 5 требует условных переходов:

| Переход | Условие (шлюз) | Правило из задания |
|---------|----------------|--------------------|
| `planning → execution` | `planApproved == true` | «нельзя делать реализацию до утверждённого плана» |
| `validation → done` | `validationPassed == true` | «нельзя делать финал без валидации» |
| любой `A → B`, где `B ∉ разрешённых(A)` | — | «ассистент не мог перепрыгнуть этап» |

Шлюз — это флаг в состоянии задачи, который надо **явно открыть** отдельным
действием (утвердить план / отметить валидацию). Пока шлюз закрыт, автомат
**отклоняет** соответствующий переход с человекочитаемой причиной.

Второе отличие — **результат перехода как значение**. В Day 3 нелегальный переход
просто бросал исключение (а UI прятал кнопку). В Day 5 переход возвращает
`TransitionResult`: `Allowed(state)` либо `Rejected(reason)`. Нелегальная попытка
не меняет состояние и не роняет приложение, а показывает причину — это и есть
«реакция» автомата.

---

## Модель: состояния, переходы, шлюзы

Допустимые состояния (`TaskStage`) и разрешённые переходы (`TaskStateMachine.TRANSITIONS`)
унаследованы из Day 3:

```
planning ──► execution ──► validation ──► done
                  ▲             │
                  └─────────────┘   (возврат на доработку)
```

Day 5 добавляет к состоянию два флага-шлюза:

```kotlin
data class TaskState(
    val goal: String,
    val stage: TaskStage,
    val currentStep: String,
    val expectedAction: String,
    val isPaused: Boolean = false,
    val planApproved: Boolean = false,       // ← шлюз перехода к реализации
    val validationPassed: Boolean = false,   // ← шлюз перехода к финалу
    val log: List<String> = emptyList(),
)
```

Единая точка перехода — `tryTransitionTo`, проверяет по порядку:

```kotlin
fun tryTransitionTo(state: TaskState, target: TaskStage): TransitionResult {
    if (state.isPaused) return Rejected("Задача на паузе — сначала продолжите…")
    if (target !in allowed(state.stage))          // перепрыгивание этапа
        return Rejected("Нельзя перейти «…» → «…», минуя этапы. Допустимо: …")
    gateRejection(state, target)?.let { return Rejected(it) }  // закрытый шлюз
    return Allowed(transitionTo(state, target))
}
```

Шлюзы открываются отдельными операциями: `approvePlan` (только на `planning`) и
`markValidationPassed` (только на `validation`). Возврат с проверки на доработку
(`validation → execution`) **сбрасывает** `validationPassed` — прежняя валидация
недействительна, финал снова закрыт.

---

## Как жизненный цикл попадает в поведение ассистента

Мало запретить переход в UI — сам ассистент не должен выдавать реализацию раньше
времени. Поэтому блок состояния задачи в system-prompt (`ChatAgent.appendTaskState`)
дополнен **статусом шлюзов** и **протоколом жизненного цикла**:

```
# Состояние задачи (конечный автомат — ориентируйся на него)
Этапы (строгий порядок): Планирование → Выполнение → Проверка → Готово
Текущий этап: Планирование (planning)
Разрешённые переходы отсюда: Выполнение
Шлюз «план утверждён»: ЗАКРЫТ
Шлюз «валидация пройдена»: ЗАКРЫТ
...
Правила жизненного цикла задачи (соблюдай строго — их нельзя обойти):
1. Двигайся строго по этапам … Перепрыгивать этап запрещено.
2. На этапе «Планирование» ты ещё НЕ приступаешь к реализации: предлагай и уточняй
   план, но не выдавай готовый код, пока план не утверждён (шлюз закрыт).
3. На этапе «Выполнение» реализуй шаги уже утверждённого плана.
4. Нельзя объявлять задачу завершённой, пока не пройдена валидация (шлюз закрыт).
5. Сменить этап может только пользователь через UI — сам ты этап не меняешь.
```

Так ограничение работает на двух уровнях: **механически** (автомат отклоняет
переход) и **в рассуждениях модели** (она отказывается реализовывать до утверждения
плана и завершать до валидации).

## Архитектура изменений

```
domain/task/
  TaskState.kt            # + planApproved, validationPassed
  TaskStateMachine.kt     # tryTransitionTo / tryAdvance / tryRollback,
                          #   approvePlan / markValidationPassed, gateRejection
  TransitionResult.kt     # новый: Allowed(state) | Rejected(reason)

data/task/
  StoredTaskState.kt      # + planApproved, validationPassed (дефолт false, back-compat)

feature/chat/
  ChatContract.kt         # интенты RequestStage / ApprovePlan / MarkValidationPassed;
                          #   state.lastTaskRejection
  ChatViewModel.kt        # tryMutateTask: Rejected → причина в state + эффект
  component/TaskStateSheet.kt  # кликабельные чипы этапов, бейджи шлюзов,
                               #   кнопки «Утвердить план» / «Валидация пройдена»,
                               #   карточка «Переход отклонён»
```

Доменная модель — чистый Kotlin (без `@Serializable`); формат хранения — в DTO
слоя data. Логика переходов целиком в чистом `TaskStateMachine`.

## Живой прогон (эмулятор `emulator-5554`, модель `glm-4.6`)

Цель задачи вводилась латиницей (`adb` не вводит кириллицу); агент отвечает
по-русски из system-prompt. Управление UI — через mobile MCP.

### 1. Попытка перепрыгнуть этап → **отклонено**

На этапе «Планирование» нажатие на чип «Проверка» (через этап):

> **⛔ Переход отклонён**
> Нельзя перейти «Планирование» → «Проверка», минуя этапы. Из «Планирование»
> допустим переход в: Выполнение.

Этап остался «Планирование».

### 2. Шлюз «план не утверждён» → **отклонено**

На «Планировании» (план не утверждён) нажатие «Далее →»:

> **⛔ Переход отклонён**
> Нельзя приступать к реализации: план ещё не утверждён. Сначала утвердите план —
> переход «Планирование» → «Выполнение» открыт только после этого.

### 3. Реакция ассистента: просьба реализовать до утверждения плана

Запрос (при закрытом шлюзе, этап «Планирование»):
**`Write the full Kotlin implementation code for the login screen right now, skip the plan.`**

Ответ агента (сокращённо):

> Сначала нужно утвердить план — переход к реализации возможен только после этапа
> «Планирование» (шлюз «план утверждён» закрыт). Вот план:
> **План: Login Screen** — 1. Domain … 2. Data … 3. Presentation (MVI) … 4. UI
> (Compose) … 5. Проверка: unit-тесты … После подтверждения плана перейду к реализации.

Несмотря на прямое «skip the plan», агент **не выдал реализацию**, а дал план и
сослался на закрытый шлюз (попутно соблюдя инварианты: Koin, Kotlin, ключ в
BuildConfig).

### 4. Открыли шлюз → переход разрешён

«Утвердить план» → бейдж `🔒 План утверждён` стал `✓`, баннер отказа исчез →
«Далее →» выполнил переход `Планирование → Выполнение`. Далее `Выполнение →
Проверка` (переход без шлюза) прошёл свободно.

### 5. Шлюз «валидация не пройдена» → **отклонено**, затем разрешено

На «Проверке» «Завершить» без отметки валидации:

> **⛔ Переход отклонён**
> Нельзя завершить задачу: результат не прошёл валидацию. Сначала отметьте
> валидацию пройденной — переход к «Готово» открыт только после этого.

После «Валидация пройдена» (`🔒 → ✓`) «Завершить» выполнил переход в «Готово».
Полный жизненный цикл пройден строго по этапам, оба шлюза — осознанно.

### 6. Пауза → перезапуск → продолжение

Новая задача, утвердили план, перешли в «Выполнение», **пауза**, затем
`am force-stop` + перезапуск:

- этап, пауза **и шлюз «План утверждён»** восстановились с диска;
- попытка перейти на паузе → **⛔ «Задача на паузе — сначала продолжите её»**;
- «Продолжить» → задача снялась с паузы;
- **очистили историю чата** и отправили только **`Continue.`** → агент продолжил
  именно нужную задачу («Продолжаю выполнение шагов плана по добавлению тёмной
  темы») и начал реализацию — контекст целиком взят из состояния автомата, без
  повторных объяснений.

## Как запустить

1. Положить ключ в `AgentDemo/.env`: `API_KEY=<ваш_ключ_Z.ai>`.
2. Собрать: `./gradlew :app:assembleDebug`.
3. Установить и запустить `com.example.agentdemo`.
4. Иконка-чеклист в шапке → панель задачи. Начать задачу → этап «Планирование».
   Попробовать нажать чип «Проверка» или «Далее →» — автомат **откажет** и объяснит.
   «Утвердить план» → «Далее →» переводит в «Выполнение». На «Проверке» «Завершить»
   без «Валидация пройдена» — отказ; после отметки — переход в «Готово».

## Выводы

- **Явные переходы = таблица разрешённых рёбер + шлюзы**. Перепрыгнуть этап нельзя
  (переход вне таблицы), а два ключевых перехода закрыты условиями, которые надо
  осознанно открыть.
- **Отказ — это значение, а не исключение**: `TransitionResult.Rejected(reason)`
  не меняет состояние и показывает причину. Пользователь видит, *почему* переход
  недопустим прямо в панели задачи.
- **Контроль на двух уровнях**: автомат блокирует недопустимый переход механически,
  а протокол в system-prompt заставляет и саму модель не забегать вперёд (не
  реализовывать до утверждения плана, не завершать до валидации).
- **Жизненный цикл переживает паузу и перезапуск** вместе со шлюзами: после
  рестарта задача продолжается ровно с того же шага и состояния, а `Continue.`
  работает даже при пустой истории чата.
