# Week 2 · Day 5 — Три стратегии управления контекстом + переключатель

## Условие задания

Реализовать в агенте **три стратегии управления контекстом** (минимум) и
переключатель между ними:

1. **Sliding Window** — хранить только последние N сообщений, остальное отбрасывать.
2. **Sticky Facts / Key-Value Memory** — отдельный блок `facts` (ключ→значение) с
   важными данными диалога; обновлять его после каждого сообщения пользователя; в
   запрос отправлять `facts` + последние N сообщений.
3. **Branching** — сохранить checkpoint, создать от одного места 2 ветки,
   продолжать каждую независимо, переключаться между ними.

Протестировать на одном сценарии («собираем ТЗ, 10–15 сообщений»), прогнать на
каждой стратегии и сравнить по качеству, стабильности (не теряет ли детали),
расходу токенов и удобству.

**Результат:** агент с тремя стратегиями + сравнение.

## Что сделано

За основу взят агент из [Week 2 · Day 2](../day-2/) (Android-приложение
**AgentDemo**, Clean Architecture + MVI + многомодульность, DI на Koin,
персистентность истории в JSON). Проект скопирован в `AgentDemo/` этого дня и
дополнен слоем управления контекстом с переключаемыми стратегиями. Для метрики
«расход токенов» перенесён `TokenEstimator` + `HeuristicTokenEstimator` из
[Day 3/4](../day-4/).

Ядро задания — доменный сервис **`ContextManager`**: по активной
`ContextStrategy` он решает, **что именно** из накопленной истории уйдёт в модель.
Переключается стратегия сегментированным переключателем в шапке (**Окно / Факты /
Ветки**), выбранная стратегия и её данные персистятся и переживают перезапуск.

### Как устроена каждая стратегия

| Стратегия | Что уходит в модель | Доп. запрос к LLM |
|-----------|---------------------|-------------------|
| **Sliding Window** | только последние `N=6` реплик, старое отбрасывается | нет |
| **Sticky Facts** | блок фактов (ключ→значение) + последние `N=6` реплик | да, +1 на сообщение (извлечение фактов) |
| **Branching** | вся история активной ветки целиком | нет |

- **Sliding Window** — `history.takeLast(N)`; оставляет контекст ограниченным, но
  теряет всё, что уехало за окно.
- **Sticky Facts** — отдельный порт `FactsExtractor` (реализация `LlmFactsExtractor`)
  после каждого сообщения пользователя дёшево (low temperature) обновляет набор
  фактов и возвращает его JSON-объектом `{"ключ":"значение"}`. Факты уходят
  отдельным `system`-сообщением, поэтому важное держится в контексте, даже когда
  окно последних реплик его уже не захватывает.
- **Branching** — модель `BranchingState` (ветки + активная + индекс чекпоинта).
  Чекпоинт фиксирует точку, форк создаёт **Ветку A** и **Ветку B** от неё, активная
  ветка живёт в ленте, снапшоты веток — в состоянии. Переключение сливает текущие
  сообщения в снапшот активной ветки и подставляет выбранную.

Поток данных (дополнен управлением контекстом):

```
UI (MVI, выбор стратегии)
   → ChatViewModel ──ask(strategy, history, facts)──→ AskAgentUseCase
                                                         ├─ FactsExtractor (Sticky Facts: +1 запрос)
                                                         ├─ ContextManager.prepare(strategy) → что слать
                                                         ├─ Agent → LlmClient → Z.ai
                                                         └─ TokenEstimator → ContextStats (метрика)
   ← AskOutcome(reply, facts, stats)
   └─ conversation.json  +  context_state.json  (стратегия/факты/ветки переживают перезапуск)
```

Агент остаётся **чистой функцией** «(запрос, история, факты) → ответ»: он лишь
получил необязательный `facts`-блок отдельным system-сообщением. Вся логика выбора
контекста живёт в домене (`ContextManager`) и use case, а не в агенте и не в UI.

## Живой прогон сценария «сбор ТЗ» (эмулятор `emulator-5554`)

Один и тот же сценарий: на 1-й реплике называем **бюджет 5000 USD**, затем
несколько реплик ТЗ (платформа, цвет, напоминания) — так, чтобы бюджет уехал за
окно `N=6`, — и в конце просим **напомнить бюджет**. Промпты на английском — `adb`
не вводит кириллицу.

### 1. Sliding Window

После 4 реплик ТЗ спрашиваем бюджет (он уже вне окна из 6 реплик):

> **Вопрос:** *What exact budget did I mention at the very start?*
> **Агент:** «**Ни одного бюджета вы не упоминали.**»

Статус: `≈170 ток. (6 реплик)`. Ранний факт **потерян** — окно его отбросило.

### 2. Sticky Facts

Тот же сценарий. После каждого сообщения панель «Липкие факты» наполняется;
к моменту вопроса в ней 5 фактов:

```
• бюджет: 5000 USD
• цель: собрать ТЗ для проекта
• платформа: Android
• цвет: синий (основной акцент)
• напоминания: каждые 2 часа
```

> **Вопрос:** *What exact budget did I mention at the very start?*
> **Агент:** «**5000 USD**»

Статус: `≈306 ток. (6 реплик)`. Бюджет **восстановлен из блока фактов**, хотя та
реплика давно вне окна. Цена — ~в 1.8× больше токенов на запрос и +1 запрос к LLM
на каждое сообщение пользователя (извлечение фактов).

### 3. Branching

Строим общий ствол (1 обмен про fitness-app), ставим **Чекпоинт** на сообщении
№2, создаём **2 ветки**:

- в **Ветке A**: *«Decision: build it natively in Kotlin»* → агент одобряет Kotlin;
- переключаемся в **Ветку B**: Kotlin-реплики исчезают из ленты, остаётся только
  ствол; *«Decision: build it cross-platform in Flutter»* → агент одобряет Flutter;
- возвращаемся в **Ветку A** и спрашиваем выбранную технологию:

> **Вопрос (в Ветке A):** *Which technology did we choose? Answer with one word.*
> **Агент:** «**Kotlin**»

Ветки **независимы**: решение Flutter живёт только в B и не протекает в A.
Переключение чипами **Ветка A / Ветка B** мгновенно меняет ленту.

Сборка `assembleDebug` — зелёная.

## Сравнение стратегий

| Критерий | Sliding Window | Sticky Facts | Branching |
|----------|----------------|--------------|-----------|
| **Качество ответа** | хорошее, пока всё нужное в окне | лучшее на длинном диалоге: важное всегда под рукой | зависит от ветки; внутри ветки — полный контекст |
| **Стабильность (детали)** | ❌ теряет всё за окном (бюджет «не упоминали») | ✅ ключевые факты не теряются (бюджет = 5000 USD) | ✅ в пределах ветки; между ветками — изоляция |
| **Расход токенов** | 🟢 низкий и **ограниченный** (окно фиксировано): ≈170 | 🟡 выше (факты+окно) + **скрытый +1 запрос/сообщение**: ≈306 | 🔴 **растёт без границы** — вся ветка целиком |
| **Удобство** | просто и предсказуемо; молча забывает старое | «память» видна в панели; чуть дороже и медленнее | мощно для «а что если» / A-B сравнения; требует ручного управления |

### Выводы

- **Sliding Window** — дешёвый и предсказуемый дефолт: держит контекст
  ограниченным, но на длинном диалоге молча теряет ранние договорённости. Для
  «сбора ТЗ» рискованно — важные требования уедут за окно.
- **Sticky Facts** — лучший баланс для длинных деловых диалогов: важное (цель,
  бюджет, ограничения, решения) живёт в компактном блоке и не зависит от окна.
  Платим токенами (факты в каждом запросе) и латентностью (+1 запрос на
  извлечение) — но именно это и видно в метрике, что честно для сравнения.
- **Branching** — не про экономию, а про **исследование альтернатив**: сравнить
  два варианта ТЗ/архитектуры от общей точки, не смешивая их. Расход токенов
  максимальный (вся ветка), зато ветки полностью изолированы.

## Как запустить

1. Положить ключ в `AgentDemo/.env`: `API_KEY=<ваш_ключ_Z.ai>`.
2. Собрать: `./gradlew assembleDebug`.
3. Установить и запустить `com.example.agentdemo`.
4. Переключателем в шапке выбрать стратегию: **Окно / Факты / Ветки**.
   - для **Веток**: «Чекпоинт» → «Создать 2 ветки» → переключаться чипами A/B;
   - для **Фактов**: раскрыть панель «Липкие факты», чтобы видеть ключ→значение.
5. Строка-метрика под переключателем показывает оценку токенов последней отправки —
   по ней удобно сравнивать стратегии вживую.
